# Non-isolated playback feasibility review

> **Historical research — production approach dropped / intentionally removed.** The decision in [runtime requirements](NON-ISOLATED-REMUX.md) supersedes recommendations and next steps below. JSPI/Asyncify experiment harnesses and private runtime builds were removed; retained evidence describes prior execution only. No new experiments accompany this decision.


Reviewed 2026-09-21 against the dirty working tree at `3bfeac8`. This is an architecture and regression-risk review, plus a bounded Asyncify experiment. It does not implement the migration or certify full playback parity. No production source, served Wasm, or routing defaults were changed during this review.

**Conclusion:** JSPI with an Asyncify fallback is viable for the maintained remux engine. The same approach is a credible extension for the bounded audio-adaptation engine. Standalone external ASS rendering has a simpler synchronous worker interface and may need neither suspension mechanism. Full Hybrid/Software and embedded mpv subtitles are substantially different: their current implementation depends on libmpv threads and synchronization. They cannot safely become non-isolated by changing link flags or swapping shared buffers for ordinary buffers.

The earlier suggestion that the entire existing player could simply become one non-threaded implementation with two builds was too broad. Two suspension builds can share a suitable engine. Creating that suitable engine for all current mpv responsibilities remains major work.

**Evidence and scope**

- [Reviewed file hashes and external cached mpv source provenance](../results/nonisolated-feasibility/20260921T234251Z/inputs.json). A concurrent change to `src/unified-player.ts` was detected and the relevant call sites were [rechecked](../results/nonisolated-feasibility/20260921T234251Z/recheck.json); the conclusions were unchanged.
- [Asyncify browser results](../results/nonisolated-feasibility/20260921T234251Z/result.json), [link command](../results/nonisolated-feasibility/20260921T234251Z/command.json), and [experiment harness](../results/nonisolated-feasibility/20260921T234251Z/check-asyncify.mjs).
- [Existing contract-test results](../results/nonisolated-feasibility/20260921T234251Z/contracts.log): 29 passed across audio worklet, retained video geometry, timing coalescing, plan admission, worker-remux control, and packaging contracts.
- The experiment used Emscripten 4.0.14 and existing no-pthread FFmpeg archives. It compiled the maintained remux C with Asyncify into a private build directory. No production assets were replaced. Both Chrome 152.0.7977.83 and Firefox 146.0.1 ran with the JSPI APIs explicitly unavailable, on a non-isolated origin, with an unshared Wasm heap.
- In each browser, asynchronous probe/open/start/step calls produced a four-second H.264/AAC TS remux whose independently decoded pixels and PCM exactly matched the source. This verifies suspension and remux output for that fixture. It does not verify MSE playback, production RangeReader authorization/cancellation, seeks, performance, mobile browsers, full decoding, or subtitle parity.
- The raw-export negative control deliberately withheld the source read forever. `await engine._rm_open(...)` nevertheless returned `0` after issuing one read in both browsers. Using `ccall(..., {async:true})` waited correctly in the positive test.

**Findings, in priority order**

1. **High: libmpv threading is an architectural dependency, not an optional decoding optimization.** [native/player.c](../native/player.c) calls `mpv_create()` and initializes the libmpv renderer. The cached pinned mpv implementation inspected for this review creates `core_thread` inside `mpv_create()` (`player/client.c:623`), and its push audio output creates an AO thread (`audio/out/buffer.c:585`). Our [browser AO](../native/ao_browser.c) implements that push interface. [Hybrid linking](../scripts/link-hybrid.sh) and [Software building](../experiments/software-full/build.sh) explicitly link pthread mpv and FFmpeg libraries with a worker pool. Disabling FFmpeg decoder threads does not remove the mpv core, audio, demux, or renderer coordination. A clean migration must either port that scheduling model cooperatively or implement an alternative backend and establish feature parity. Neither is a small build-system change.

2. **High: the current Wasm invocation pattern is wrong for an Asyncify variant.** [native-remux-worker.js](../web/native-remux-worker.js) awaits raw `_rm_probe`, `_rm_open`, `_rm_start`, and `_rm_step` exports. This works with the configured JSPI exports but does not wait for an instrumented raw Asyncify export, as reproduced above. Introduce one serialized invocation adapter that uses the proper API for each build. Preserve the existing one-operation-per-engine invariant. Cancellation must not reenter a suspended engine to call close or free its state; terminate the owner or cancel the read, settle the operation, and then close. Heap views must be refreshed after suspension and growth.

3. **High: shared PCM buffers carry clock and reset semantics, not just samples.** [ao_browser.c](../native/ao_browser.c) derives delay and available space from consumed frames and output latency. [software-full-engine-worker.js](../web/software-full-engine-worker.js) and [filter-retained-engine-worker.js](../web/filter-retained-engine-worker.js) copy between the Wasm ring and the worklet ring, with generation acknowledgments. [audio-worklet.js](../web/audio-worklet.js) does not advance media consumption for underrun silence and rejects stale generations. A message transport must preserve those rules. Merely posting PCM chunks and driving time from enqueue timestamps would regress seeks, pause/resume, EOF, and A/V synchronization. Use bounded transferable buffers, consumption acknowledgments, generation-tagged reset/pause commands, and audio-output clock mapping. The existing 8192-frame capacity is about 171 ms at 48 kHz; transport feedback and decode scheduling must fit a deliberately measured budget, not an assumed one.

4. **High: non-isolated software codec fallback does not exist yet.** The current fallback is the isolated [WasmPlayer](../src/internal/wasm-player.ts), and [plan admission](../src/internal/playback-plans.ts) explicitly rejects Hybrid/Software without isolation. Hybrid's [native decoder bridge](../native/vd_browser.c) uses futex waits and a shared mailbox to the retained decoder worker; its retained-frame path intentionally escalates browser-decoder failure to a public Software reopen rather than returning software frames through the same renderer. An alternative backend needs compressed-packet transport, browser configuration/flush handling, FFmpeg decoding, frame ownership, and a shared presentation scheduler. Keeping the public mode names does not establish equivalence.

5. **High: broad audio conversion and subtitle parity exceed a suspension port.** [flac.h](../native/adaptation/flac.h) deliberately accepts a narrow set of integer-precision mono/stereo sources; both codec contexts already request one thread. Its build enables PCM/FLAC/DTS decoding and FLAC/optional Opus encoding, with resampling disabled. It is a good candidate for a no-pthread build, but that alone does not unlock AC-3, MP3, arbitrary floating-point conversion, downmixing, or unsupported layouts. Those need codec inventory, conversion policy, timestamps, encoder-delay and drain tests. Similarly, [standalone ASS](../native/subtitles/ass.c) consumes already-loaded bytes and timestamps in one worker, whereas [embedded subtitles](../native/subtitles/service.c) directly includes mpv's client implementation and accesses core locks, demuxing and subtitle state. Rebuilding standalone libass does not replace the embedded subtitle service.

6. **Medium: engine selection is distributed across admission, probing, loading and packaging.** [source-probe.js](../web/source-probe.js), [native-remux-player.js](../web/native-remux-player.js), the mux worker, and [EnginePreparation](../src/internal/engine-preparation.ts) independently select or assume the engine. Preparation chooses the JSPI inspector solely from isolation state. [package-beta.py](../scripts/package-beta.py) enumerates fixed engine names, and [verify-beta-release.py](../scripts/verify-beta-release.py) requires a JSPI-specific exact-archive suite. Adding only a worker fallback would leave probing, prewarming, or installed packages broken. Share a versioned runtime descriptor and ensure precompiled module caches include engine kind, suspension variant, ABI, and build identity. Use distinct dependency prefixes for pthread and non-pthread builds; the base build scripts currently inject `-pthread` into dependencies.

7. **High: existing media correctness holes must not be hidden by runtime fallback.** The prior review in this conversation reproduced admission of a different audio track from the one FFmpeg selected, and VP9/Opus falling back to MP4 with incorrect decoded audio length. Current source still independently selects the admitted and runtime audio streams, and WebM remains a preference rather than a correctness requirement. Resolve a source stream identity once and revalidate on track changes. Restrict packaging to choices that preserve required edits/padding. JSPI-to-Asyncify fallback must be limited to capability or variant initialization failures; source identity, authorization, codec, and timeline errors need their existing specific handling.

**What can be shared cleanly**

| Component | Reusable boundary | Work still needed |
| --- | --- | --- |
| Native direct / Shaka | Existing browser-owned playback and clock | Keep independent of Wasm suspension selection |
| File remux / inspector | Maintained C, bounded source worker, packet output | Dual builds, invocation adapter, shared loader, complete lifecycle tests |
| Bounded audio adaptation | Maintained FFmpeg decode/encode functions, one-thread contexts | Non-threaded dependency build, variant loading, conversion and output qualification |
| External ASS | Timestamp-driven libass API and transferred bitmap tiles | Non-threaded library build, matching asset ABI, visual parity; Asyncify may be unnecessary |
| File/range source policy | RangeReader, LocalFileReader, identity/auth policy | Typed requests and generation-aware cancellation; preserve the separate ResourceLoader open/read/close semantics for manifests |
| Audio output | AudioWorklet and consumption/reset invariants | New message transport and measured clock feedback |
| Video presentation | Retained frame ownership, geometry and YUV/RGB rendering utilities | Decouple scheduling from mpv while preserving timestamps, color, rotation, and seek preroll |
| Player control | Backend interface and transactional source/mode replacement | Explicit feature/command parity; current properties and commands are substantially mpv-shaped |

Ordinary workers and transferred buffers allow multiple independently owned components without shared Wasm memory. They do not recreate pthread shared address spaces. Avoid moving long software decode work onto the main thread, and avoid making the AudioWorklet depend on synchronous replies from a decoding worker.

The suspension variant should be an internal runtime property, not a new public playback mode or a duplicated routing tree. One module factory and invocation interface can normalize JSPI and Asyncify. Select and validate the variant in the execution worker; communicate its descriptor to preparation and diagnostics. If JSPI-specific initialization is unavailable, terminate the candidate and start a fresh Asyncify instance. Do not fetch both variants eagerly or mix a compiled module with the other variant's glue.

**Regression-controlled sequence**

1. Fix stream-selection and padding-preservation holes and strengthen the expanded remux tests to measure actual source-time/frame advancement. Capture a versioned baseline of current public behavior and exact artifacts.
2. Add the shared descriptor, invocation adapter and isolated dependency prefixes. Introduce Asyncify for remux/inspection behind an explicit test selection. Require the full existing lifecycle suite on both variants, not just this experiment. Keep the accepted pthread path during migration.
3. Build and qualify standalone ASS and the existing bounded adaptation profiles without pthreads. Separate lossless precision requirements from explicitly permitted lossy conversion; do not infer wider codec support from a successful link.
4. Prove the full-decoding boundary before expanding admission: non-isolated software video plus message-delivered audio, pause/resume, forward/backward seeks, rate changes, subtitles, EOF and cancellation. Run both suspension variants. Decide here whether maintaining a cooperative mpv port is realistic or an alternative backend is required. The code review does not establish that a cooperative mpv port is clean or maintainable.
5. Implement complete backend parity and browser/software recovery. Preserve one audio/presentation clock owner per session, exact selected stream identities, and rollback of failed candidate opens. Keep preview extraction isolated from the primary playback engine.
6. Add exact-package browser evidence, then promote individual qualified plans. Remove pthread execution only if functional parity and measured throughput/latency on the target device/media matrix justify doing so. No existing performance evidence establishes that today.

**Required validation before claiming no regression**

- Parameterize common contracts by runtime variant; run non-isolated JSPI and forced Asyncify, plus the retained isolated baseline. Tests must assert which runtime executed and that non-isolated paths have no shared heap. Keep runtime capability absence and initialization-failure negative controls.
- Sources: remote ranges and local Files, large offsets, authorization refresh, bounded reads, changed identity, aborted reads, replacement and independent players. Manifest fallback also needs nested-resource origin, byte-range, refresh and cancellation checks.
- Media: actual selected tracks with distinct content; audio/video-only; AAC priming and MP4 edits; Opus startup/end padding; reordered video and nonzero A/V offsets; unequal tails; codec/configuration changes; channel order and supported sample rates. Compare decoded content and presentation timestamps separately.
- Audio: consumed-frame acknowledgments, underrun silence, pause/reset acknowledgments, stale chunks and stale feedback after seeks, AudioContext suspension, rate changes, drain and EOF. Use browser output timing evidence in addition to Node worklet simulations.
- Video/subtitles: post-seek presented frames, frame closure, retained queue bounds, rotation/SAR/color, external and embedded subtitles, font attachment ownership, subtitle switching and delay. Replacing mpv scheduling also requires filter and playback-speed parity.
- Recovery/lifecycle: browser decoder rejection, asynchronous decoder failure, MSE packaging rejection, close while a Wasm call is suspended, rapid seeks, teardown of every worker and worklet, memory-growth view refresh, and no change to accepted playback after candidate failure.
- Performance: compare identical media on the same devices for startup, sustained throughput, dropped frames, underruns, A/V drift, seek latency, memory and CPU. Establish target budgets before enabling the new backend; passing a short fixture or measuring binary size is not a performance qualification.
- Packaging: exact archive tests for every supplied runtime, source/binary correspondence, variant-aware preparation/copy-assets, and clean consumer tests. Existing JSPI-only release gates cannot certify Asyncify or a new decoder backend.

No feasibility review can promise that unimplemented code will not regress. The supported decision is to proceed incrementally with the contained engines while treating full mpv replacement/cooperative scheduling and audio-clock parity as explicit architectural milestones, not already-solved implementation details.
