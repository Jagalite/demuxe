# MediaBunny adapter release review inventory

This is a review aid for the isolated `feature/mediabunny-provider-adapters` worktree at HEAD `9702315e7aac272c718cd14ae190b8b37b7a3140`. It is not a review approval or a release qualification. The original checkout is separate. The [machine-readable inventory](../packages/provider-mediabunny/qualification/stream-handoff-core-review-inventory.json) binds all current core inputs, the HEAD blobs, the existing qualification record and the inventory script by SHA-256.

The current core manifest lists 236 inputs. Seventeen differ from or are absent at this worktree's HEAD: 14 modified files and three new files. The other 219 are unchanged from HEAD, but only 26 of those match the existing qualification record; 43 differ and 150 are unrecorded. Across all 236 current inputs, the existing record contains 79 paths: 26 current hashes match, 53 differ and 157 are unrecorded. HEAD itself is not a qualification. The current local core candidate's input inventory agrees with these 236 current hashes. The [previous inventory](../packages/provider-mediabunny/qualification/core-review-inventory.json) predates the streaming handoff fix.

Release-mode core assembly fails at `src/adapters/videojs.ts`, which is unchanged from HEAD but differs from the recorded qualification. The [failure output](../packages/provider-mediabunny/qualification/core-review-release-gate-failed.txt) is retained. That first failure is not the entire drift; updating one hash would not review the other inputs. The qualification record was not changed. The optional package remains private and its `prepack` guard rejects release packaging.

The [retained Firefox seek diagnostics](../packages/provider-mediabunny/qualification/reader-firefox-hevc-seek-diagnostics.json) identify the failure more narrowly: initial playback reached readiness, then the 2-second seek timed out with an empty buffered range in both runtimes, despite 11 seek-generation fragments totaling 2,259,355 bytes each. The reported audio evidence was presence and clock advancement, not decoded-audio proof. Both retained logs include TrueHD lossless-check warnings; whether they relate to the seek failure is unknown. The deployment lacked the hybrid player assets, so these runs cannot establish whether mpv fallback would recover. The diagnostic verifier checks both failures and four negative controls; it does not establish a root cause or release qualification.

A [separate HEVC/DTS-HD comparison](../packages/provider-mediabunny/qualification/reader-hevc-dtshd-control-verification.json) ran the otherwise untested fifth fixture in Firefox 157 with the same test-owned deployment. Both runtimes reached initial readiness and then timed out at the 2-second seek with an empty range after producing 12 seek fragments each. The DTS-HD candidate was selected; fixture and deployment hashes were checked and four negative controls passed. This separate fixture makes a TrueHD-only explanation insufficient for these observations, but both cases use HEVC MP4/FLAC presentation, and it does not establish the underlying cause or fallback behavior.

In a [captured MediaSource comparison](../packages/provider-mediabunny/qualification/reader-hevc-mse-comparison-verification.json), Chrome 155 and Firefox 157 received byte-identical HEVC/DTS-HD seek output: Chrome buffered `[3, 8.381]` and Firefox exposed no range. A fresh MediaSource replay reproduced this result; a two-second timestamp offset did not make Firefox buffer the seek data. To isolate tracks, host FFmpeg 8.1.2 remuxed the captured packets into separate MP4 files: Firefox buffered the FLAC-only file but not the HEVC-only seek file, while both browsers buffered the HEVC-only initial file at zero offset. FFmpeg's `trace_headers` reports first VCL NAL type 20 (IDR) for the initial segment and 21 (CRA) for the seek segment. The track-isolated files have different packaging, and this correlation does not establish CRA as the cause or justify a production change. The capture and replay harnesses are diagnostic only; captured bytes and host traces remain in `/private/tmp` and are required to rerun the local verifier.

The [preroll replay comparison](../packages/provider-mediabunny/qualification/reader-hevc-preroll-verification.json) appended initial IDR-bearing media before the identical seek fragments, with and without a second initialization segment. Firefox retained only the initial short range while Chrome added the later range. Three longer initial prefixes likewise did not give Firefox the complete seek range. These synthetic appends do not establish that a properly generated continuous decode from a prior IDR would fail; they show that simply prepending the captured initial fragments is not a demonstrated fix. Five fragment-identity negative controls passed; rerunning requires the local captured bytes.

An existing external `provider-mpv-complete` archive declares `@demuxe/provider-mpv` version `0.3.0-beta.4` and requires that exact `demuxe` peer version. It cannot simply be composed as a compatible fallback with the tested `1.1.2` core. A compatible mpv distribution and its qualification are still needed for a meaningful fallback test.
