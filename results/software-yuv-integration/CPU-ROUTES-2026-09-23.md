# Software RGB versus existing YUV presenter: CPU decision

**Decision: yes, qualify the existing YUV presenter for a finite SDR 8-bit 4:2:0 Software route set. Do not switch production defaults yet.** All three measured MPEG routes saved browser-process CPU in every fresh-build pair at equivalent playback cadence. Full-frame RGB/YUV comparisons still differ around chroma edges, so fidelity admission remains open. ProRes Proxy 10-bit 4:2:2 is not eligible: the YUV asset uses its RGB fallback. This is a production qualification task, not a new presenter design.

The paused seek screenshots from each matched arm showed the same source pattern, but the full-frame pixels were not identical. Over all nine RGB/YUV screenshot pairs, mean absolute RGB-channel error was 1.786–1.803/255, p99 error 26–27/255, and about 1.8% of channels differed by more than 16/255. The differences repeat exactly across the three rounds per case. Their concentration around chroma edges is consistent with different interpolation or chroma siting in mpv swscale and the WebGL linear sampler, but this cause has not been isolated. Center patch equality therefore does **not** establish unchanged frame fidelity. Production qualification must decide a fixture-appropriate tolerance and compare decoded/reference frames, including chroma edges and text, before admitting any route.

## Attribution and execution path

Automatic and forced Software selected the same Software plan, worker and RGB presenter for all four fixtures. Explicit `softwarePresenter: 'experimental-yuv'` changes the optional engine asset and presenter inside that Software worker; mpv still owns demux, FFmpeg decode, audio, timing and the frame scheduler. The three MPEG inputs produced `yuv420p` in mpv's `video-params`; ProRes produced `yuv422p10`. The automatic route attempts are preserved in the route-probe JSON.

On RGB, mpv's software render backend calls `mp_sws_scale` to bilinearly scale and convert the decoded YUV into `rgb0` directly in a 1920×1080 Wasm output buffer. This conversion is in mpv's render path, after FFmpeg decoding. Each frame then copies **8,294,400 bytes** from Wasm into reused `ImageData`, writes 2,073,600 alpha bytes, and calls `putImageData` for the full canvas. The steady windows allocated no new `ImageData`. Browser-internal Canvas copies or GPU transfers are unknown.

On eligible YUV, the native backend passes the decoded three plane pointers synchronously to the JS presenter. It copies **777,600 bytes/frame** (960×540 YUV420) row by row into three reusable JS staging arrays, then submits three WebGL texture uploads totaling the same 777,600 bytes. The shader performs BT.601 conversion and 2× display scaling. No staging allocation occurred during the measured windows; GPU execution and driver-internal copies are not included in the JS upload-submit timer. YUV retains the RGB output allocation and has a separate Wasm asset, so this is not a general memory-saving result.

The timers are wall time and overlap: `_web_render` includes the YUV draw callback, and the WebGL phase timers sit inside that callback. **They are not added to claim CPU.** In a representative fresh TS window, RGB had 368 frame render calls totaling about 2.65 s and YUV had 372 totaling about 0.20 s. RGB post-render JS copy/alpha/put cost about 1.9 ms/frame; YUV plane staging about 0.09 ms/frame. This identifies presentation as a material fraction of RGB work and is consistent with the separate end-to-end process CPU reduction.

The runtime counters showed roughly 1,200–1,600 null/no-frame render calls per window, taking about 1–3 ms total, 60–61 diagnostics posts taking about 1–4 ms, no steady `ImageData` or YUV staging allocation, and no steady worker or I/O messages after warmup. Audio pump and event handling took single- to low-double-digit milliseconds. The scheduler still wakes frequently; these measurements do not identify a meaningful idle-pump saving from switching presenter. PCM queue depth was sampled, but video decoder queue depth and individual FFmpeg-thread CPU were unavailable. The residual YUV process CPU includes decoding, demux, audio, JavaScript, WebGL/browser work and scheduling. It cannot honestly be labeled a measured decoder cost or used to prove a codec is decoder dominated.

## Eligibility boundary and next task

The present native guard only uses GPU YUV for `IMGFMT_420P`, BT.601/709 matrix and non-PQ/non-HLG transfer, with quarter-turn rotations allowed by code. That is narrower than all Software output and still needs a stricter production admission contract. The observed CPU candidate subset is **SDR 8-bit planar 4:2:0, BT.601 limited, unrotated, 960×540 decoded to 1920×1080 display**, plain video. Static color patches additionally exercised BT.601/709 full and limited range, but full-frame chroma-edge fidelity is still pending. Ten-bit, 4:2:2, 4:4:4 and other pixel formats use RGB fallback; ProRes here is 4:2:2 10-bit. HDR/PQ/HLG, wide-gamut SDR transfer/primaries, nonstandard matrices, rotation, arbitrary crop/aspect, unusual or negative strides, different scaling ratios, and long-run GPU lifecycle have no fresh CPU-and-fidelity qualification from this run. The animated subtitle result is a separate correctness observation, not a CPU estimate.

The measured CPU win is sufficient to justify a **small/medium, finite production qualification task** for the three named SDR 8-bit 4:2:0 routes. Its first gate is resolving or explicitly accepting the reproducible chroma-edge differences; then pin asset provenance, add explicit color/format admission, compare cadence across target browsers and devices, and retain RGB fallback for every unqualified output. Do not switch the default based on this Chrome/M1 run alone. No new presenter, WebGPU decoder, or default-route change was made here.
