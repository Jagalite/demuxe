# Hybrid retained-video presentation CPU — 2026-09-23

**Recommendation: MEASURE MORE.** None of the correct visible test presenters consistently recovered most of the earlier 19–29 core-point blank-display bound. A simple Canvas2D draw retained the current scheduler and did not reproducibly reduce total CPU. Direct WebGL2 upload and WebGPU external-texture presentation were visible and functional, but their total Chrome CPU often exceeded production in reverse-order runs. The present evidence does not justify promoting a presenter or opening the independent-audio/native-video project.

## Current frame path

`retained-decoder-worker.js` submits compressed packets to `VideoDecoder`. Its output `VideoFrame` is transferred to the engine worker; Hybrid writes only a 2×2 placeholder to Wasm, with no full-frame `copyTo`. The engine worker indexes retained frames by timestamp, holds at most a few frames, waits for mpv's selected serial/PTS/delay, draws on the worker's transferred 960×540 OffscreenCanvas, draws the subtitle overlay, and calls `_web_presented`. It retains one displayed frame for redraw and closes replaced/stale frames. `retained-video.js` calculates pixel aspect/rotation/fit, then does `save`, black `fillRect`, `translate`, `rotate`, `drawImage(VideoFrame)`, and `restore`. There is no ImageBitmap or explicit full-frame JS pixel allocation in production Hybrid. The browser's internal VideoFrame-to-canvas import, scaling, and compositor work are not exposed as copy bytes.

For each mpv selection, the current worker creates one pending-request object and a timer when the deadline is in the future; the frame and request Maps update on receipt/draw. Bounded lateness/PTS diagnostic arrays append one number per presented frame and serialize their recent tail every 200 ms. The test WebGL2 path reuses one GL texture but calls `texImage2D` per frame; the WebGPU path creates an external-texture view, bind group, and command encoder per frame. The tested fixtures select no subtitles or video filters. The production subtitle overlay still receives its per-frame read/draw call, while the minimal/GPU ablations skip it.

Test instrumentation counted decode submissions and frames, transfer/receive/close, selected/drawn/redrawn frames, retained/pending peaks, selected-frame lateness, per-arm draw calls and synchronous JS time, PCM frames/underruns, and per-process CPU. A representative 320 H.264 production window received, drew, and closed 364 frames in 12 seconds; a 1080p60 production window received/closed 718 and drew 717 at the window boundary. Retained queue peaks were 4–5 and pending peak 1; no growth appeared across CPU windows or lifecycle checks, and no missing-frame error occurred. Boundary differences between decoded and drawn counts of a few frames are window timing, **not** a reliable compositor-drop counter. Native `<video>` reported zero dropped frames in its measured windows. This campaign did not expose GPU copy bytes or a direct hardware-decoder identity.

## What the ablations isolate

- The `about:blank` control used 30.7, 24.6, and 30.3 core points, almost entirely in Chrome's browser process. An independent OS `ps` CPU-time check then measured 3.69 and 3.75 browser-process CPU seconds in successive 12-second idle windows (30.7% and 31.3%). Four `SystemInfo.getProcessInfo` calls each took 1–2 ms and added no measurable OS CPU time, so the idle result is not CDP polling overhead. Thus a 20–30 point browser-process term can exist **without any media** in this host/session. Its cause was not identified, and it cannot safely be subtracted from a different playback window. This control rules out attributing all browser-process swings in the arm sequence to video decode or presentation. [OS/CDP cross-check](idle-metric-check-20260923.json).
- On 320 H.264, the low browser-process round used 25.6 production, 19.6 no-draw, 31.4 minimal Canvas2D, 39.0 WebGL2, and 44.0 WebGPU core points. On 1080p60, the reverse order ended at 24.4 production and 11.0 no-draw, while WebGPU had risen to 50.5 earlier in the same order. The blank deltas of 6.0 and 13.4 points in those low-browser-load windows are still **upper bounds** because no visible replacement can omit drawing altogether.
- Same-player 320 H.264 production/no-draw/production was 41.9 / 36.0 / 54.2. The browser process alone moved 29.2 / 31.3 / 44.5 points; renderer+GPU moved 12.3 / 4.3 / 9.3. Same-player 1080p60 was 55.7 / 49.2 / 43.8; browser moved 35.5 / 41.5 / 22.4, while renderer+GPU moved 19.7 / 7.4 / 21.0. Visible drawing therefore induces roughly 5–13 renderer/GPU points in these fresh H.264 brackets, but the whole-family delta cannot be assigned precisely while browser-process work shifts this much. [Small no-draw bracket](h264-small-same-player-nodraw-20260923/result.json), [1080p60 bracket](h264-1080p60-same-player-nodraw-20260923/result.json).
- Synchronous 320 production draw/subtitle calls took 110–120 ms for about 360 frames in 12 seconds (0.9–1.0% of one core by wall time); 1080p60 production took 129–155 ms for about 720 frames (1.1–1.3%). Measured selected-frame bookkeeping beyond those calls took about 19–23 ms per 12 seconds in the production samples, and frame receipt/bookkeeping 2–5 ms. This does not include every idle pump poll. These timings are not CPU attribution for asynchronous raster, browser import, GPU, or compositor work. There was no explicit `VideoFrame.copyTo` on this route.
- Same-player production/minimal-Canvas/production at 1080p30 was 72.1 / 55.8 / 42.7 and at 1080p60 was 63.1 / 53.3 / 49.8. Browser-process CPU fell across both sequences while renderer+GPU did not show a stable gain from the direct draw. Minimal Canvas2D therefore does not validate `fillRect`/save/restore/geometry as the main cost. [1080p30 same-player](h264-1080p30-same-player-canvas-20260923/result.json), [1080p60 same-player](h264-1080p60-same-player-canvas-20260923/result.json).
- WebGL2 spent about 0.5–1.1 seconds of synchronous call time per 12-second 1080p/320 window in `texImage2D(VideoFrame)` and drawing, compared with about 0.07–0.16 seconds for WebGPU and production Canvas2D. WebGL2 also increased GPU-process CPU on the 320 fixture. This is not evidence of a cheaper path. WebGPU uses a direct external texture with no explicit CPU readback, but reverse-order totals and GPU CPU do not show a repeatable saving.
- The native video-only reference is a ceiling, not a whole-player competitor. It lacks AC-3 decode/output and the mpv/WebCodecs clock bridge. Even native video-only shifted from 9.1 to 33.9 points at 1080p60 as its browser process rose from 0.2 to 27.7; this confirms that a single low native number cannot establish selective-audio savings.

In the 320 low browser-load round, production Hybrid was 25.6 against native video-only 6.0; the best tested GPU presenter was WebGL2 at 39.0. At 1080p60 the low-load production/first-order WebGPU/native observations were 24.4 / 23.7 / 9.1, but WebGPU became 50.5 in reverse order. These gaps include all of Hybrid's audio/demux/runtime work and cannot be read as the cost of its presenter or the benefit of an audio-service redesign.

## Visible correctness and limits

Both GPU candidates passed H.264 small-fixture pause/held-frame/resume, forward and backward seek, 1.5× rate, EOF, and cleanup with no surviving surface. At 11-second seek the top marker pixel was green `(0,109,0)`; after seeking backward to 2 seconds it was red `(255,24,0)` for both presenters. Screenshots show correct 16:9 geometry and moving markers; frame counters progressed and retained queues stayed bounded. [WebGPU lifecycle](webgpu-correctness-h264-20260923/result.json), [WebGL2 lifecycle](webgl2-correctness-h264-20260923/result.json). The CPU windows had no audio underruns. At EOF the worklet's cumulative underrun counter rose after playback exhausted media; that boundary needs separate policy interpretation before any promotion.

The test GPU and minimal Canvas paths deliberately omit subtitle drawing, filters, arbitrary pixel-aspect and rotation geometry. The measured fixtures have square pixels, zero rotation, 16:9 video, and no subtitle/filter output. Thus the visible CPU result is a codec/fixture experiment, not a generic replacement qualification. No native-video/audio synchronization was implemented or measured.

## Decision

The prior 19–29 point no-draw number is a blank-display **ceiling**, and the fresh same-player trials plus idle Chrome control show browser-process variation large enough that a single actual presentation total cannot be defended. The reproducible synchronous retained-frame bookkeeping is below 0.3 core point in a 12-second window; optimizing Map/timer JS alone cannot recover most of the ceiling. Canvas2D's browser import/raster/compositor is a plausible substantial cost, but changing only the final Canvas2D operation did not reliably help. WebGL2 did not lower total Chrome CPU; WebGPU's best 1080p60 window did not reproduce and its HEVC low-browser-load window was worse than production. The native reference leaves audio/demux/sync out of the workload, so the residual gap does **not** yet justify a native-video plus independent software-audio route.

**Next measurement gate:** identify the idle Chrome browser-process workload with call stacks/tracing, record the actual WebCodecs decoder/backend during each phase, then rerun the H.264 320/1080p30/1080p60 counterbalanced visible arms with a concurrent idle-process baseline and stable browser/backend state. Compare renderer+GPU and total Chrome CPU for the same frame PTS/cadence, and require a repeatable visible saving of at least 10 core points across the realistic fixtures before considering a production presenter. A native-video plus audio study should wait until a qualified visible WebCodecs presenter still leaves a separately measured residual gap after selected-audio costs are included.
