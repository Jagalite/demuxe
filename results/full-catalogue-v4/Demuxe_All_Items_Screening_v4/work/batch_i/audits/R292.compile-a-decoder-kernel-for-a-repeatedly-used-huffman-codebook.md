73: 
74: **First experiment.** Baseline sequential grayscale JPEGs sharing tables. Compare the same decoder with its ordinary prederived lookup tables, a specialized kernel, and native ImageDecoder where qualified. Require identical symbols, consumed bits, quantized coefficients, and reconstructed output. Exercise long codes, byte stuffing, restart boundaries, truncation, table changes, invalid tables, and first-frame behavior.
75: 
76: **Safety and lifecycle.** Untrusted tables are bounded data, never arbitrary supplied instructions. Limit code size, compilation budget, cache entries, and input-derived loops; validate generated modules and obey deployment compilation policy. Wasm module validity does not establish correctness or resource safety of the generator. Fall back when compilation is unavailable, too costly, or a table is not reused.
77: 
78: **Measure.** Kernel construction, validation/compilation, first frame, steady state, compiled-code retention, full decoder cost, and break-even count. Compare against an optimized table-driven decoder, not a naive binary-tree traversal.
79: 
80: **Reject.** Lookup machinery already captures the useful specialization, instruction/cache cost rises, tables change too often, or total work grows. No guaranteed speedup from replacing loads with branches.
81: 
82: **Distinction.** R226 changes legal source Huffman coding to suit a decoder; this changes a controlled decoder to suit the unmodified source. R145 selects broad build-time profiles; this specializes runtime codebooks.

65: ## R292 — source-specialized JPEG Huffman Wasm kernel
66: 
67: A deterministic 256×256 grayscale JPEG was encoded with a reused validated Huffman table set. The prototype parses the actual JPEG DHT/scan, removes byte stuffing at the entropy-wrapper boundary, and supplies entropy bytes to two Wasm paths sharing the same coefficient reconstruction logic:
68: 
69: 1. an ordinary canonical table-driven Huffman decoder;
70: 2. a generated source-specialized kernel whose Huffman decisions are emitted as fixed codebook-specific Wasm control flow.
71: 
72: The JPEG contains **1,024 8×8 blocks**, **56 stuffed 0xFF bytes**, and AC codes as long as **16 bits**. Both paths consume the same final bit position and reproduce **every quantized coefficient exactly** against libjpeg's coefficient oracle.
73: 
74: A second JPEG uses restart interval 32 and contains **31 restart markers** plus 60 stuffed bytes. Both paths again reproduce every coefficient exactly after the wrapper resets predictor/alignment at restart boundaries.
75: 
76: The specialized coefficient output was written back through libjpeg using the original critical parameters. Its decoded grayscale pixels are byte-exact to the original JPEG.
77: 
78: Median kernel timings over alternating benchmark rounds:
79: 
80: - ordinary table-driven: **1.5305 ms**;
81: - specialized: **1.2255 ms**;
82: - **1.25×** kernel speedup.
83: 
84: Restart case: **1.5387 → 1.2191 ms (1.26×)**.
85: 
86: Negative controls:
87: 
88: - truncated entropy returns an error;
89: - an optimized-coding JPEG has a different Huffman-table hash and therefore cannot hit this specialization;
90: - an oversubscribed synthetic Huffman table is rejected by validation;
91: - restart and byte-stuffing cases remain exact.
92: 
93: The combined Wasm module is 5,469 bytes. First `WebAssembly.Module` construction measured ~0.39 ms in this Node host, but this is not a production break-even claim because the module contains both compared paths and the prototype's offline C/Clang generation is not a runtime code generator. Native `ImageDecoder` is unavailable in this browser, so that comparison is BLOCKED.
94: 
95: **Boundary:** this proves a specialized entropy/coefficient kernel, not a full Wasm MJPEG player speedup.
