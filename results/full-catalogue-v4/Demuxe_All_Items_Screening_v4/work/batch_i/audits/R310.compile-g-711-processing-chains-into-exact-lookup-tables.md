114: ## R310 — Compile G.711 processing chains into exact lookup tables
115: 
116: **Class:** Exact finite-input-domain processing specialization.
117: **Output contract:** Byte-identical output to one fully pinned decode/process/re-encode recipe; the requested processing and companding may intentionally alter samples.
118: **Related:** R292 specializes decoding code; this specializes the whole stateless processing chain.
119: 
120: ### Mechanism and basis
121: 
122: G.711 PCMA/PCMU encode a sample in one octet [S5]. FFmpeg exposes A-law/mu-law conversion functions and conversion tables, so ordinary table-based decoding must be part of the baseline [S6].
123: 
124: For a fixed samplewise operation P and pinned decode/encode maps D and E, compile:
125: 
126: T[a] = E(P(D(a)))
127: 
128: For two aligned inputs and a fixed mix-plus-nonlinearity recipe Q:
129: 
130: T[a,b] = E(Q(D_A(a), D_B(b)))
131: 
132: There are 256 input values in the first case and 65,536 pairs in the second. An eight-bit-output two-input table occupies 64 KiB. A two-input table can replace explicit decode, mixing, memoryless clipping/processing, and re-encoding steps at runtime.
133: 
134: ### First pilot
135: 
136: Two aligned PCMU streams, matching sample clocks, fixed rational mix weights, an exactly specified rounding rule, a fixed memoryless clipper, and pinned PCMU output encoding. Enumerate every input pair and compare its table result against an independent implementation of the complete recipe.
137: 
138: Then process realistic packet traces while preserving sample order, layout, timestamps, and total duration. Apply the same test to PCMA only as a separately identified profile.
139: 
140: ### Negative controls
141: 
142: The alternative zero codes where present; all polarity combinations; extrema; quantization transitions; one changed processing parameter; mixed channel order; wrong table identity; and unaligned sample timelines.
143: 
144: Stateful filters, attack/release dynamics, arbitrary gain automation, and random dithering are excluded initially. Continuous parameter interpolation between tables does not automatically reproduce the original operation. Rebuild an exact table or use the ordinary path.
145: 
146: ### Baseline, measurements, and rejection
147: 
148: Compare against an optimized fused implementation that already uses codec conversion tables and avoids unnecessary PCM buffers. Count table construction, code/data footprint, cache misses, number of concurrent profiles, and complete packet handling.
149: 
150: This is not lossless restoration of pre-G.711 audio. It reproduces a declared processing/re-encoding result. Reject when simple existing arithmetic is faster, table churn dominates, or the workload has too few samples to amortize setup.
151:

42: ## R310 — Compile G.711 processing chains into exact lookup tables
43: 
44: G.711 has only 256 possible input codewords per law. The lab enumerates every μ-law input and every A-law input through the same deterministic, stateless FFmpeg chain (`volume=0.75, volume=-1.0`) and stores each resulting output code as a 256-entry table.
45: 
46: On one million arbitrary input samples, table lookup is **byte-for-byte identical** to running the full FFmpeg decode/filter/re-encode path for both laws. A shuffled-order control also matches, verifying the tested chain is sample-local rather than history-dependent.
47: 
48: The observed host-process-to-lookup ratios (~57.2× μ-law, ~58.9× A-law) are not a production speed forecast because the FFmpeg side includes process startup and filter-graph overhead. The durable result is the exact finite-domain compilation. Stateful filters, resampling, dithering, packet loss concealment and history-dependent gain cannot use a simple 256-entry LUT this way.
