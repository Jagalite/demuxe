## R206 — Incremental MJPEG stripe decode/upload

libjpeg exposed each 64-row RGB stripe while decoding a 1024×768 JPEG. The first stripe was available at **0.313 ms**, versus 2.678 ms for the complete image. WebGL accepted those stripes through repeated `texSubImage2D()` calls into a texture that remained unpublished until completion. The partial negative-control pixel differed from the final published pixel.

Median full-frame texture upload was 0.900 ms versus 1.000 ms for all stripe uploads, so there is **no standalone upload-speed win** here. The open opportunity is overlap between decode and upload; this pilot did not benchmark an actually overlapped pipeline. The graphics implementation is SwiftShader-class software, not physical-GPU evidence.

## First-pass decision

Hypothesis: The proposed mechanism 'Incremental MJPEG stripe decode/upload' may provide the specified output with less work or add a faithful route for its stated profile.

Contract: Complete exact JPEG image publishes only after final stripe; partial decode/upload may overlap but incomplete textures are never visible.

Current gap: Presenter gets complete mp_image/VideoFrame outputs, not partial libjpeg stripes. Overlap would require a decoder stripe callback and unpublished-texture owner; multiple uploads alone showed no reported gain.

Cheapest correct baseline: Current complete JPEG decode followed by one full texture upload.

Primary outcome: User-visible operation latency, duplicated work or peak/steady live resource ownership; not object counts alone. No numerical outcome was measured.

Bounded next test and falsifier: Expose one bounded stripe callback and completion fence only if existing decoder permits it; compare complete pixels and withhold publication until final stripe, with partial-frame negative control.

Reopen only when the named missing contract/owner exists, a concrete workload exposes removable work, or the stated next slice changes this finding. A historical report assertion is not a newly verified current result.

Limits: per-mechanism source screen only; code/test presence does not prove successful runtime. No generic family verdict or missing-source inference was used.
