# Decision-first protocol and effort limits

## One decision, not one feature

The minimal unit is a mechanism plus its input/output contract and source identity. First pass asks whether more investigation is justified. It is not a promise to implement the entire card or reproduce every historic lab result.

| Tier | Work allowed | Enough to decide | Not enough to claim |
|---|---|---|---|
| A: source/current-code audit | Read the definition and one relevant owner; use an existing trace or test result. | Already implemented, no applicable workload, decisive precondition failure, expensive setup, or a useful next experiment. | Runtime speed or complete-route correctness. |
| B: tiny prerequisite/component probe | One exact API/configuration gate, numerical identity, packet/header construction or bounded synthetic example. | Advance or hold a sharply scoped branch; reject an incorrect variant with a preserved counterexample. | Matching Wasm/browser integration, physical output or broad support. |
| C: localized real-path screen | Existing build/harness; one small change and at most one diagnosed repair; smallest useful positive case plus adverse control. | A worthwhile signal or added capability worth confirmation; a scoped failure; insufficient evidence; no observed bottleneck. | Production readiness, whole-corpus reliability, broad cross-browser behavior or a release decision. |

Start at A and stop when its answer is enough. Never require C for every item. A theoretical or source-level blocker can be decisive without a new build. If a successful A/B probe merely repeats a known primitive, record the remaining integration gap rather than treating that as a newly promising optimization.

## Default effort envelope

One candidate revision plus one targeted corrective revision; one newly generated tiny fixture only when needed; one focused oracle extension; and reuse of existing build/harness machinery. This is a scope budget, not a completion-time estimate.

Use a small shared build for compatible localized native patches only when real-path execution is affordable. A new runtime family, codec parser, byte provider, preview service, state serialization system, ownership framework or physical hardware dependency exceeds first-pass scope. Record DEFER_SETUP or HOLD_ENV and the exact next slice; continue elsewhere.

A fix to an observer is not a candidate improvement. Preserve the broken-observer run and the corrected independent control. Re-measure only if that observer affected the claim.

## Reuse setup without blending verdicts

Keep U (unchanged maintained artifact), R0 (research artifact all switches off), and R1 (one candidate enabled) distinct when switchable builds are used. Check U versus R0 before attributing R0 versus R1 to a single mechanism. Separate artifacts are preferable when toggles alter code generation or ABI fidelity.

One shared capability probe can hold several dependent records. Record the probe hash and the specific dependency per item. Do not rebuild/reprobe the same unavailable capability for every ID, and do not mark a whole family passed when one member worked.

Parallelize source reading or tiny independent fixture work only in isolated workspaces. One coordinator owns the ledger. Serialize scored timing and avoid concurrent builds on the measured device. Actual subagents are optional; no unprovided subagent tool is assumed.

## Minimal executed checks

Preserve the requested output and source identity. Use one positive case and one adverse control that can specifically disprove the mechanism. Include the relevant boundary: for example, an ineligible channel precision, a non-RAP seek, stale generation, changed table, incorrect buffer stride, or a canceled consumer. Run cleanup. Add one short seek/EOF operation when the changed path could affect it; do not impose a full universal matrix on a one-line source audit.

Output capture, full hashes and heavy observers belong in diagnostic runs. A timing run can use lightweight counters after its exact build/fixture correctness has been established. Keep observer cost explicit and compare the same requested operation, not a candidate with missing features.

## Small measurements

Choose a primary metric and practical worthwhile change before timing: startup/seek latency, CPU seconds per operation, maximum live bytes, transferred bytes, correct capability, or repeated-query cost. Avoid a universal threshold.

For a timing-dependent screen, one warmup and roughly three alternating pairs can reveal a large directional signal. Expand up to the earlier small seven-pair screen only when that would decide the next step cheaply. These are suggested caps for triage, not statistical-power guarantees. Save every run, ordering and warm/cold condition.

A few pairs may justify ADVANCE_CONFIRMATION because a next test is worthwhile. They rarely justify claiming a stable percentage or rejecting a marginal benefit. If plausible effects straddle the worthwhile threshold, mark INCONCLUSIVE; specify whether the follow-up is worth doing. Do not use a seven-run maximum as a p95. Do not reuse the R74 5% or R27 10% contract globally.

An obvious incorrect-output counterexample, absence of the supposed code path, exact zero work at that boundary, or an unavailable required API may justify stopping without any timing. A positive capability can matter without lower CPU. Host, algebra, canvas, native, software-GPU and physical-GPU results remain separate evidence types.

## Local failures are scoped

Reproduce a failure only far enough to classify it. Distinguish broken control media, intentional admission rejection, toolchain/environment failure, candidate regression and real source/ownership defects. Do not call every failure a baseline blocker for every item.

If a serious authority or correctness problem is found, hold the affected family and retain the reproduction. Do not raise timeouts, strip requested tracks, weaken precision guards or change output contracts to turn it green. Continue independent healthy work.

## After a decision

Write a result record, retain the supporting source/log/patch references, and move to the next untouched item. Reopen only for a stated changed condition. Use the confirmation queue for survivors; during this breadth campaign it is a backlog, not an automatic next action.

First-pass coverage is complete only when every named record has a documented decision or scoped blocker and every missing slot has a source-gate entry. Report executed coverage separately. Source-blocked items remain scientifically unevaluated.
