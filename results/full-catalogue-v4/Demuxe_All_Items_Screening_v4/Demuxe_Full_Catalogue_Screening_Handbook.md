# Demuxe: screen the full research catalogue

**Version 4.0 · 19 September 2026 · Local-agent operating handbook**

## 1. Decision-first, across the full pool

The assignment is a breadth-first screening campaign over all available research mechanisms, ordered by practical impact and ease of reaching a trustworthy decision. It replaces the previous tactical 17-item shortlist. A first-pass outcome means “worth further testing / not currently worthwhile / already implemented / duplicate / blocked / expensive setup / inconclusive,” not “feature shipped.”

The package accounts for all **366 legacy IDs**. It contains **392 ranked source-defined mechanism records** across **333 IDs**, preserving **59 additional meanings behind reused numbers**. There are **33 missing-definition slots**, separately listed and never replaced with guesses. These counts describe provenance coverage, not independent successful experiments or industry novelty.

There are **60 source documents** and individual linked assignment cards. Most are full recovered reports or proposal attachments; some early original proposals are normalized conversation extracts. Raw fixture/benchmark archives are not comprehensively included. Missing definitions are R76–R81, R247–R260 and R276–R288.

A serious current correctness or authority issue can preempt its affected path. Otherwise keep moving. Do not spend the entire session confirming R27 or rebuilding a preview service while hundreds of named records remain untouched.


## 2. What the first pass should produce

Each item gets one source-bound decision and a concise evidence record. A source audit can be sufficient when the code already does the proposed work, the necessary content is absent, the promised saving cannot affect the stated outcome, or the next implementation exceeds the allowed scope. A prerequisite query can hold an unavailable browser/GPU/runtime surface without a build. A tiny component or real-path probe can establish a counterexample or enough promise to justify the next phase.

A positive cheap screen is not complete qualification. Preserve its evidence level. Likewise, a rough proxy losing to optimized upstream code rejects that implementation/comparison, not necessarily the general mechanism. No forced pass rate, rejection quota, universal percentage threshold or developer-hour forecast is used.

Use a bounded next-test description for a promising item and put it in the confirmation backlog. The default campaign allocates **no automatic deep-confirmation work** before finishing the first-pass pool; the user can authorize a separate survivor campaign later.


## 3. Ranking policy

Impact and screen effort are separate from later qualification burden. Impact I5 can change a route or preserve required features; I4 can remove substantial operation work; I3 is a useful conditional stage; I2 is a narrow specialty; I1 is low current value. E0 means inspect/probe, E1 a local harness/JS change, E2 a localized matching native change, and E3 an architecture/oracle/device gap. Q1–Q4 describes only later qualification burden.

The starting matrix is in protocol/PRIORITIZATION.md. It favors consequential cheap decisions, then core-playback relevance, impact, smaller screen cost and smaller later burden. A high-ranked E0 gate does not authorize a high-cost implementation when the gate succeeds. Exposure and gain are unmeasured until the local audit.

Every recoverable record has a rank. Re-score with a written reason when actual code, workload, shared setup or stronger evidence changes the cost/value. Review likely overlap explicitly; do not multiply success counts for closely related variants, and do not close another mechanism because its R-number matched.


## 4. Reusable setup and strict effort envelope

Locate the authorized checkout and existing harness. Record the actual revision, diff and relevant served artifact identity. Establish only the unchanged baseline needed by the selected family. Existing lossless and ASS controls are dependencies when used, not global requirements before a source-read audit.

Default per-item implementation budget: one small candidate, at most one diagnosed correction, and at most one new tiny fixture when the existing corpus is insufficient. Reuse a focused observer. Compatible native changes may share compilation, but must be enabled and compared separately. Verify the all-off research artifact against the unchanged maintained reference.

Stop before a new service, broker, player, full decoder, serialization framework, delivery backend or toolchain family is necessary. Give that item DEFER_SETUP or HOLD_ENV with its exact prerequisite. Broad test matrices, large new corpora, endurance and physical-output tests are not first-pass defaults.

Only one coordinator writes the ledger. Independent reading or fixture work can be parallelized in separate workspaces; scored timing is serialized without competing builds. Actual subagent support is optional, not assumed by the package.


## 5. Minimum honest experiment

Before executing, state the hypothesis, admitted profile, requested output, cheapest correct maintained baseline, primary metric and falsifier. Read the actual source section: the generated assignment is not a substitute for codec state, timeline or numerical requirements.

Use one clear positive case and one adverse control targeting the shortcut's assumption. Preserve required audio/subtitles/effects, configuration, sample/frame identity, source generation and cleanup. Add only the short seek/EOF/cancellation operations the patch can plausibly affect. Do not call buffer acceptance, a stable object, a flag or silent fallback proof of actual candidate output.

A source-bound code audit can stop without timing. When timing is needed, a tiny paired set may show a large directional signal; if not, mark uncertainty rather than inflating repetitions until it looks good. Separate heavy output observers from performance runs. Include cold preparation, indexing, conversion, copies, worker coordination and teardown in the chosen complete operation. No component percentage automatically becomes a whole-player saving.

A browser destination test using a host-preconverted file is not in-browser adaptation. A mathematical or CPU proxy is not a tested GPU route. Exact digital samples are not physical display/speaker or energy qualification. Intentional lower quality, downmixing or altered playback remains a separate explicit output contract.

## 8. Operating the queue

From the extracted package root, verify and inspect the initial state:

```sh
python3 tools/screening.py verify
python3 tools/screening.py status
python3 tools/screening.py next --limit 12
```

Read the selected card, produce a template, then record a filled decision with actual package-relative evidence paths:

```sh
python3 tools/screening.py show R343
python3 tools/screening.py template R343 > decision.json
python3 tools/screening.py record decision.json
```

A bare ambiguous R-number is rejected. Choose its full key. The tool checks local source hashes, evidence-file existence and content hashes, required scope fields, and stronger requirements for claimed real-path execution. It does not certify that an agent's reasoning or test is valid, and it never executes tests itself.

The first-pass lane excludes completed reported screens unless explicitly reopened. The source lane covers missing definitions; import covers inherited findings; followup lists survivors without starting them. Use reprioritize and reopen only with an actual reason. Changes are appended, not silently substituted into historical records.


## 9. Finish and resume

After each item: preserve its diagnosis or result, exact candidate/source/build identity, evidence type, limitations, next test and reopening condition; then continue. At a session boundary report fresh decisions, untouched records, accounted blockers, actual executed probes and follow-up candidates separately.

“Every item accounted for” is not “every item tested.” Do not equate a source recovery hold or an API blocker with a passing experiment. Do not require a success or failure for every idea when evidence is inconclusive. A complete first pass can contain useful stops and holds.

When the user commissions a later phase, confirm selected survivors with broader controlled measurements and real workloads, then qualify combinations and release profiles. Until then: no publication, route-default changes, licensing changes, unrelated upgrades or production subsystem rollout.

The successful output of this campaign is a complete, reproducible decision ledger across the full research pool—not a handful of deeply polished prototypes and hundreds of forgotten cards.
