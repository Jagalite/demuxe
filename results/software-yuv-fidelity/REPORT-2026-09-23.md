# Software YUV fidelity attribution, 2026-09-23

## Disposition: B. QUALIFY ONLY A NARROWER SUBSET

The existing opt-in YUV path had a real left-sited chroma phase bug. It sampled U/V at the luma normalized coordinate, which means **center-sited** chroma for even-sized 4:2:0 images. MPEG-2/4 and the measured H.264-style frames declare **left-sited** chroma. The small correction passes mpv's chroma-location offset into the existing YUV shader and maps each chroma plane with its own dimensions. Production RGB remains the default.

The repeatable RGB/YUV screenshot discrepancy also included a **legitimate reconstruction difference**: mpv's configured fast `SWS_BILINEAR` conversion reconstructs 4:2:0 chroma more coarsely than libswscale with full chroma interpolation or WebGL `LINEAR`. The RGB presenter is faithful to that fast mpv conversion; it is not a ground truth for chroma-edge fidelity.

## Exact current paths

The RGB Software backend uses `libmpv_sw.c` → `mp_sws_scale` → RGB0 output buffer; `native/player.c` sets `sws-fast=yes`, `sws-scaler=bilinear`. `sws_utils.c` sets libswscale source chroma position, color coefficients and range from `mp_image_params`. It crops its source pointer after rounding the crop origin down to pixel-format alignment, scales and converts to destination dimensions, then mpv draws OSD/subtitles on the RGB image. The Software worker copies the full RGB frame from Wasm into `ImageData`, fills alpha, then calls `putImageData`.

The opt-in YUV backend accepts 8-bit planar 4:2:0 and passes Y/U/V pointers and strides to WebGL. The presenter copies each plane row into contiguous staging storage, uploads three `R8` textures with `LINEAR` filtering and edge clamp, and draws at the mpv destination rectangle. Before correction it used `c = crop.xy + uv * crop.zw` for all planes. The corrected chroma coordinate is `c * (sourceSize / (2 * ceil(sourceSize/2))) - chromaOffsetInLumaPixels / (2 * ceil(sourceSize/2))`, separately in X and Y. For an even-width left-sited source this is a positive **0.5/sourceWidth** horizontal normalized shift, or a quarter chroma texel. Center-sited chroma has zero shift. `pl_chroma_location_offset` supplies the signed source offset. The YUV subtitle surface is a separate RGBA texture blended after the video draw.

For both matrices, the shader first forms `Y/255`, `(U-128)/255`, `(V-128)/255`. Limited range expands luma by `255/219` after subtracting `16/255` and chroma by `255/224`; full range does not expand. BT.601 uses `(1.402, -0.344136, -0.714136, 1.772)` and BT.709 uses `(1.5748, -0.187324, -0.468124, 1.8556)` for the usual R/G/B combinations. The render target clamps and quantizes to 8-bit. No transfer-function conversion or HDR tone mapping occurs; the tested decoded output is SDR. Exact-value patches across all four matrix/range combinations have at most 1/255 error against full-chroma libswscale.

## Geometry and composition

- With the left-sited correction, 2× and noninteger upscales, 0.5× and noninteger downscales, odd destination sizes, and aspect-preserving letterbox were tested on vertical edges, checkerboard, diagonal edges and luma ramps. Against the explicitly matched full-chroma bilinear reference, max error is **2/255**, p99 at most **1/255**; an independent CPU bilinear texel-center calculation also differs by at most 2/255. `NEAREST` WebGL sampling was run as a control and did not match the bilinear reference at chroma boundaries. Thus the large legacy RGB/YUV edge difference is the old fast RGB chroma filter, rather than a scaling coordinate error after correction.
- Even X/Y and odd X, Y and X+Y crop origins all reproduced the corresponding pixels in the full corrected WebGL image exactly at 1:1. Padded Y/U/V strides also reproduced the contiguous result exactly. This validates the shader's luma/chroma coordinate mapping for the direct path, including odd crop phase. **It does not qualify arbitrary crop metadata through the actual player**: the RGB backend rounds crop origins down to format alignment, so an actual odd crop can intentionally differ. Nonzero visible rectangles should get a separate player-level qualification.
- A 65×49 4:2:0 source with alternating chroma produced max/p99 **143/136** between full-chroma libswscale and corrected WebGL. WebGL matched the independent chroma-site bilinear calculation exactly. The cause of libswscale's odd-source reconstruction difference is not established here, so **odd source dimensions remain outside admission**.
- A controlled 8×6 half-alpha red overlay on gray changed exactly pixels `x=9..16, y=7..12`; an interior pixel was `[193,65,65]`, the expected blend over `[130,130,130]`, and all underlying pixels outside the bounds were unchanged. The animated subtitle player case passed subtitle uploads, four seeks, resize, context loss/recovery, paused redraw equality, and cleanup (`results/software-yuv-integration/yuv-chrome-2026-09-23T18-06-23.319Z/result.json`). This validates composition positioning, alpha/color, and redraw separately from video conversion for that case.
- Four actual-player color patch cases (BT.601/709 × limited/full) passed after the correction with **0/255 center-patch error**, no YUV fallback and no player errors (`results/software-yuv-integration/yuv-chrome-2026-09-23T18-15-46.685Z/result.json`). `npm run build:software-yuv` and `npm run build` passed.
- A focused ProRes `yuv422p10` player check confirmed **4 RGB fallback frames and no errors** ([fallback.json](./fallback.json)). A separate legacy `tenbit` qualification command could not start because its `build/fixtures/playback-performance/h264-10bit.mkv` fixture is absent in this checkout; its timeout is not a pixel-format result (`results/software-yuv-integration/yuv-chrome-2026-09-23T18-16-22.574Z/result.json`).

## Proposed production admission predicate

This is a **future** bounded task; it is not enabled by this experiment. Admit only a Software-decoded frame when all conditions hold:

1. Decoded format is **planar 8-bit YUV420P** (`IMGFMT_420P`), with positive strides and even source width/height. The frame's visible rectangle is the entire decoded frame, with no rotation; ordinary tested destination scaling and letterbox are allowed.
2. The **frame metadata reaching the presenter after mpv normalization** resolves to **BT.601 or BT.709 matrix**, **limited or full range**, and **left or center 4:2:0 chroma location**; reject remaining `UNKNOWN` values. Require a supported SDR transfer (BT.1886 for the measured real routes), with no PQ/HLG or HDR metadata. This accepts the measured AVI's mpv-normalized BT.601/limited values even though FFprobe reports source matrix/range as unspecified. That evidence establishes YUV fidelity to mpv's interpretation, not the source creator's undocumented color intent.
3. Keep 10-bit, 4:2:2, 4:4:4, ProRes yuv422p10, HDR, rotation and unusual/unknown pixel formats on RGB fallback. Keep odd source dimensions and nonzero source crop outside this initial predicate. Subtitles use the separately tested composed overlay path; more subtitle formats require their own composition check.

The measured high-value TS, PS and AVI routes meet this predicate. The opt-in corrected YUV path still accepts some cases outside it; this report does not broaden the production route or change defaults. The earlier matched CPU reductions motivate a small/medium admission task, but **CPU was not rerun after this fidelity correction**, per the requested scope.

## Reproduction

`cc experiments/software-yuv-fidelity/reference.c -o build/yuv-fidelity-reference $(pkg-config --cflags --libs libswscale libavutil)`; then `node experiments/software-yuv-fidelity/probe.mjs`, `geometry.mjs`, `real.mjs`, `player.mjs`, `real-player.mjs`, and `subtitle.mjs` from the repository root. `npm run build:software-yuv` rebuilds the opt-in engine after `native/yuv-backend.c` changes; `npm run build` validates the browser package. The actual subtitle lifecycle check is `CASES=animated node experiments/software-yuv-integration/qualify.mjs`.
