# H.264 + AAC / MP4: paired CPU investigation

The measured file is the exact `aac.mp4` in `build/head-to-head/assets-release-supplement-20260925-04`, SHA-256 `37670a8ef2c82d8d99ef9b66e7cd68ee7fc74e279a86e4e7d248f4cc22bb0b4d`. It is H.264 High 320×180 at 30 fps plus 48 kHz stereo AAC, 36 seconds. Its bytes match the September 20 baseline file. The current player is the frozen release supplement snapshot, served by the same repository fixture server for plain video and Demuxe. The server is outside Chrome CPU accounting.

Five counterbalanced rounds used separate fresh headed Chrome 153.0.8010.53 launches per arm. Orders were idle/plain/Auto, Auto/plain/idle, plain/idle/Auto, idle/Auto/plain, and plain/Auto/idle. All used the same Chrome channel and `--autoplay-policy=no-user-gesture-required` flag, Playwright default temporary profile strategy, 960×540 viewport at device scale 1, 5-second warmup, 20 nominal measurement seconds, and CDP `SystemInfo.getProcessInfo` CPU-time differences divided by actual wall time. `ps` provided process command classification and summed RSS. A sixth idle/plain/Auto sequence used one Chrome launch with a new context/page for each arm; it is diagnostic and excluded from five-round medians. Raw per-tick process, state, RSS, Media-domain and error records are in [raw.json](raw.json). Two interrupted setup attempts (`-01`, `-02`) produced no complete experiment and are excluded.

All CPU figures below are percent of one core. Each category is the median of five accepted windows; **Min–max** is the whole-Chrome range. Category medians need not sum exactly to the whole median because each is calculated separately. Audio is Chrome's `audio.mojom.AudioService`; utility is its network and storage services.

The five **paired Auto − plain whole-Chrome deltas** were −10.0, +0.9, +10.3, −3.7 and +1.7 points (median **+0.9**). No round showed a reproducible +8-point wrapper cost. Forced Native Direct was not run: Auto reported `native-direct` in every window and was the same browser-owned A/V plan. The matched non-browser deltas (renderer + GPU + audio + utility, excluding browser) were −5.7, −0.6, +3.9, −0.4 and +0.6 points (median **−0.4**). Non-browser totals had medians 13.0 for plain and 12.9 for Auto. The first Auto window's renderer/GPU use was unusually low despite normal frame advance; retaining it makes the variance visible.

Fresh-launch browser-process CPU was 32.2–34.6 points at idle, 25.4–31.8 for plain playback and 25.7–33.2 for Auto. The paired Auto − plain browser-process differences were −4.4, +1.5, +6.4, −3.3 and +1.1 points. The same-browser sequence also moved from 30.8 idle to 40.4 plain and 32.1 Auto browser-process points. This variability exists within playback conditions and even within one launch; subtracting a fixed idle value would be misleading. The paired plain − idle whole deltas were +9.9, +12.0, +3.0, +10.8 and +10.7 points; Auto − idle was −0.1, +12.8, +13.3, +7.1 and +12.3. These are descriptive differences, not a stable normalized CPU measure. Same-browser whole totals were 31.0 idle, 53.4 plain and 45.9 Auto; Auto − plain was −7.5, of which −8.3 came from the browser process, while its non-browser sum was +0.8.

All 15 fresh-launch windows were accepted: process IDs remained stable, playback stayed visible and focused, no player errors were recorded, and media time advanced normally from about 5.2 to 26.4 seconds. Plain presented 634–636 frames and Auto 631–638; all recorded zero dropped frames. CDP Media properties reported `FFmpegVideoDecoder` and `FFmpegAudioDecoder` for both, with both platform-decoder flags `false`. Auto diagnostics reported the Native direct plan. Actual windows were 21.0–21.3 seconds because CDP/state/RSS samples add wall time to the nominal 20-second sleep schedule. Median peak summed RSS was 830 MiB idle, 938 MiB plain, and 970 MiB Auto; these sums can double-count shared pages and are not incremental ownership measurements. Chrome network/storage utility CPU was at most about 0.07 point per window; no other CDP-listed process contributed materially.

## Historical methodology audit

The exact approximately 20.2/21.9 row is the September 20 `cpu-baseline-performance-original-02` run: Demuxe Auto 18.6, **20.2**, 21.7 and plain video 19.9, **21.9**, 24.0 across three rounds. Its recorded browser identity was headed Chrome **152.0.7977.83**. The release supplement Auto run used headed Chrome **153.0.8010.53** and yielded 45.1, 43.9, 46.1. Both used the `chrome` channel, the autoplay flag, 960×540 viewport, device scale 1, fresh Playwright-launched browsers with temporary profiles, rotating case order, 5-second warmup and nominal 20-second CDP process sampling. Both summed all CDP-listed Chrome process `cpuTime` deltas, divided by actual elapsed wall time, and included the browser process; neither measured the fixture server or external OS media services. The file hashes and 320×180/30 fps/36-second media properties match exactly.

Material differences are Chrome version, Demuxe snapshot (`f7ad851d...` historical versus `20b5cd03...` release supplement), changed harness/adapter source hashes, and campaign scheduling: the old row paired three players for this fixture, whereas the 45.1 Auto row was measured in a broader Auto supplement with no simultaneous plain-video arm. The current five-round experiment supplies that missing matched comparator. The precise host background load and browser-process cause are not recorded in either old campaign; the Chrome version change cannot be isolated as the sole cause.

The older raw browser-process medians were 10.7 points for Demuxe and 12.5 for plain video. The release supplement Auto browser-process median was 31.5. Descriptively, the browser-process change is about 20.8 of the 24.9-point Auto whole-total difference between campaign medians; the other roughly 4.1 points came from non-browser processes. These are unmatched campaigns, so that arithmetic is an attribution clue, not a causal estimate. The current plain-video median (43.9) and Auto median (45.7) share the elevated absolute baseline.
