# Current Hybrid CPU attribution — 2026-09-23

**Recommendation: MEASURE MORE.** A selective-audio route is not yet the next qualified implementation project. The largest measured opportunity is retained-frame canvas display, but blanking the canvas overstates what a media element could save, and the video-only media-element check omits selected audio and synchronization. Chrome process CPU changed substantially between otherwise correct launches, especially for HEVC. No production route or default was changed.

## Exact routing and output

All six auto selections were plan `hybrid`: browser WebCodecs owns video decode, mpv owns demux/clock/audio decode, Demuxe owns retained-frame canvas presentation, and mpv PCM goes through the shared ring to AudioWorklet. The selected video is stream/FFmpeg index 0 and selected audio is stream/FFmpeg index 1 (`1:audio:stream:1`). The decoder submitted about 30 packets/second, produced VideoFrames, and transferred retained frames. `VideoDecoder.isConfigSupported()` returned supported with `hardwareAcceleration: no-preference`; **the actual hardware/software decoder backend was not observable**. WebCodecs support and Chrome GPU-process activity are not proof of hardware decode.

The exact auto-plan admission trace rejected Native direct for each selected MKV pair: Chrome `canPlayType()` rejected the combined H.264/HEVC + AC-3 or E-AC-3 query and rejected selected DTS audio in its queried profiles. Native packet-copy remux was unqualified for AC-3 initialization and DTS construction; Chrome `MediaSource.isTypeSupported()` rejected the E-AC-3 MP4 combination. The opt-in Native/mpv subtitle-service plan was not admitted for these files. Each trace then admitted `hybrid`.

## Direct counters and remaining blind spots

- Instrumented H.264 + AC-3 and HEVC + E-AC-3 each produced about 600 retained draws in 20 seconds. Presentation-side synchronous JS, including `drawRetainedVideo()` and subtitle overlay calls, took **76.5 ms** and **102.8 ms** total (0.38% and 0.51% of one core by wall-time accounting). Canvas/browser/GPU work after those calls is outside this timer. Retained and pending queues peaked at 4 and 1 frames; WebCodecs pixel copies were zero. EncodedVideoChunk construction still copies the small compressed input; there was no `VideoFrame.copyTo()` or full-frame Wasm pixel copy. [Instrumented results](20260923-instrumented/result.json).
- Both instrumented windows copied **962,048 stereo PCM frames** from the Wasm ring into the shared ring: **7,696,384 bytes read and 7,696,384 bytes written**. The JS loop took 5.8–6.0 ms total, about **0.03% of one core**. AudioWorklet consumed the same order of frames at 48 kHz with zero underruns. Chrome's audio service used about 0.4–0.6% of one core in the six-case steady pass. This does not include FFmpeg decode or mpv audio conversion in renderer threads.
- All six input files were fully fetched/cached before the steady window. **Logical source reads and physical bytes fetched during that window were both zero**; startup totals ranged from 14–98 logical reads and 0.9–6.4 MB fetched. No seeks occurred during the CPU window. mpv still advanced its demux cache and selected streams. Audio packet decode counts, discarded packets by stream, and demux CPU time were not exposed.
- Steady windows saw about **1,588–1,711 pump ticks** in 20 seconds. Two instrumented windows observed about **1,234 mpv events polled** and **97 diagnostics posts** each. With about 600 render outputs, roughly 1,000 render calls per window returned no new output. Property-change counts, worker wakeups, diagnostic serialization CPU, native decoder time, resampler time, and filter time were not separately measured. A cross-launch 10-second diagnostic cadence trial had higher CPU than baseline, illustrating why its subtraction cannot support an overhead claim.

## Decision on a selective-audio route

Of the proposed cost groups, **B (retained WebCodecs video/presentation)** is the strongest supported dominant region, especially the browser/GPU work induced by canvas display. The data rules out the premise that Hybrid necessarily spends most CPU on **software video decoding in Demuxe**. Video decode is active in Chrome WebCodecs; its own CPU share remains unseparated from presentation. Audio-side PCM transport is small; FFmpeg audio decode/conversion and mpv runtime remain unresolved within renderer CPU.

For a **video-only** stream copy of the same H.264 frames, a media element used 36.3% of one core between full Hybrid phases at 54.9% and 60.3%. Source and MP4 copy had identical hashes for all 1,080 compressed video packets. It omitted selected audio and any shared A/V clock. The analogous HEVC copy also had 1,080 identical packet hashes, but its CPU sequence was 49.3% Hybrid, 39.0% video-only, then 24.8% Hybrid with normal frame delivery: Chrome backend/process behavior changed enough to invalidate a savings calculation. A direct one-call canvas draw preserved these fixtures' geometry but did not show a CPU reduction in its H.264 A/B/A trial. [Native video H.264 bound](20260923-native-video-h264/result.json), [HEVC bound](20260923-native-video-hevc/result.json), [simple-draw toggle](20260923-paired-simple-h264/result.json).

**Answer:** A media-element-video plus selected mpv audio + PCM ring + AudioWorklet route *might* remove meaningful canvas work, especially for H.264, but these runs do not establish a stable end-to-end saving across the six codec pairs or justify the new demux/clock complexity. The next measurement should use 90-second, full-resolution, realistic-motion H.264 and HEVC Main10 sources with all three audio codecs at the intended channel layout; a persistent Chrome profile, isolated host, at least three counterbalanced rounds; decoder-backend trace evidence; and native mpv counters for audio packet decode, resample/layout/filter time, stream discard, and null-render/poll CPU. A test-only end-to-end candidate must then keep selected audio, seek/pause/rate/track-switch behavior, and bounded A/V drift before its CPU can be compared. No TrueHD or DTS-HD case was added because the basic split remains unresolved.
