# Optional MediaBunny adapters

Development implementation pinned to MediaBunny 1.63.0. This package is private and blocks publication until release qualification. FFmpeg/mpv providers remain maintained alternatives.

The package exports an inspector factory and a provider implementing Demuxe's existing preview contract. For format-specific delivery use `@demuxe/provider-mediabunny/inspect/mp4`, `/inspect/webm`, `/preview/mp4` or `/preview/webm`. These entries pin their formats and static runtime, and accept no loader override. The generic entry below retains its configurable full-SDK default loader. Importing the adapter does not import MediaBunny: its runtime loader runs only when an inspection or preview is requested. Callers must supply an explicit input format set; there is no implicit `ALL_FORMATS` registration or global codec registration.

```js
import {WAVE} from 'mediabunny';
import {inspectMedia} from 'demuxe';
import {createMediaBunnyInspector} from '@demuxe/provider-mediabunny';

const inspector = createMediaBunnyInspector({formats: [WAVE]});
const facts = await inspectMedia(source, {inspector});
```

The inspector hook is implemented in the accompanying core change. Core owns source normalization, validated remote transport, authorization, the inspection deadline and byte reader. The adapter receives a borrowed source and applies its own finite budget. It never substitutes MediaBunny's URL transport. Standalone inspection also accepts a Demuxe custom byte source.

Inspection always returns partial evidence: MediaBunny's A/V track list cannot establish subtitle absence, default/forced flags or complete track metadata. `completeFor` contains only `container`. Unknown channel layout, roles, sample precision and other unestablished fields stay unknown. Transport, cancellation and asset-loader errors propagate; the adapter does not choose fallback policy.

```js
import {MP4} from 'mediabunny';
import {createMediaBunnyPreviewProvider} from '@demuxe/provider-mediabunny';

const preview = createMediaBunnyPreviewProvider({
  formats: [MP4],
  getSource: sourceId => currentSources.get(sourceId) ?? null,
});
const remove = player.preview.addProvider(preview);
// Retire through the preview owner when the source/player changes.
```

The source resolver must be synchronous and perform no I/O. It must return only the source corresponding to the requested source generation. Prefer borrowed sources when the player owns their lifetime. Preview declares decoder contention and yields to playback. It returns a PNG, represented PTS and conservative accuracy/fidelity labels. Release cancels active work, disposes inputs, clears canvases (including late results) and permits subsequent reuse.

No codec extensions are registered. Existing module-global MediaBunny custom decoders can nevertheless affect upstream decoder selection; this adapter does not claim browser-native decoding when consumers have registered such decoders. Isolation/explicit decoder selection must be qualified before making that claim.

## Validation

Run `npm ci --ignore-scripts --legacy-peer-deps` and `npm test`. The unit suite includes the real pinned WAVE parser and transport/abort/budget tests. Preview contract tests use a controlled runtime; they are not browser decoder evidence.

`node test/browser-preview.mjs` additionally needs Playwright, esbuild and Chrome from the development environment. `DEMUXE_PLAYWRIGHT_MODULE` and `DEMUXE_ESBUILD_MODULE` can point to their module entry files. The browser test generates a VP8/WebM fixture using WebCodecs and the upstream writer, then reads it through the adapter. It also authors a separate Matroska container directly from EBML elements and the encoded VP8 packets, checking real native-owner startup, seek, fresh frames, decoded color and packet/configuration preservation. That fixture follows the [Matroska element specification](https://www.matroska.org/technical/elements.html) and does not use MediaBunny muxing. It does not require system FFmpeg. A fixture generated by the same library does not independently qualify arbitrary container compatibility.

The upstream declaration bundle conflicts with TypeScript 5.9's DOM WebCodecs declarations when all library declarations are checked. Demuxe uses `skipLibCheck`; this package does not patch upstream declarations. Browser runtime tests and contract checks remain separate evidence.

## Bounded local preparation

The accompanying core changes add the finite `mediabunny-file-preparation` + `browser-prepared` binding to `native-remux`. The implementation profiles are `webm-vp8-video-only-v1` and `matroska-vp8-video-only-v1`, both producing WebM: local files up to 32 MiB, exactly one VP8 video track established by the existing complete inspection owner, zero-based monotonic timestamps, no rotation, flip or transparency. A bounded source/output EBML check verifies authored block timing, rejecting lacing, invisible/discardable blocks, encrypted/additional payloads, nonzero codec delay/preroll/offset, unknown-sized clusters and explicit timing normalized by the packet API. Before publication, the adapter reparses its bounded output and requires exact packet count/order/type/size, timestamps and durations, decoder configuration, geometry, color and track metadata to match the input. A writer-induced timing or configuration change declines this preparation profile and leaves the existing preparation path available. Other sources retain the existing preparation path. Partial MediaBunny inspection cannot establish this admission by itself.

A separate `mediabunny-mp4-file-preparation` + `browser-prepared` binding provides `mp4-h264-video-only-v1` and `mov-h264-video-only-v1`, producing MP4. It uses the same 32 MiB, complete single-video, zero-start, no-transform envelope. The classic `avc1` sample tables must describe one local self-contained track, positive sequential durations, no composition offsets, and no edits except one identity edit. Fragmented input, external data references, unrecognized sample groups, other sample descriptions and nonidentity edits remain outside these profiles. The bounded authored sample-table check follows [Apple’s format documentation](https://developer.apple.com/documentation/quicktime-file-format); output metadata, packet sizes/timing and decoder configuration are checked before presentation; fixture tests additionally compare encoded packet hashes. The MP4 worker is acquired independently from the Matroska/WebM worker. Neither asset is acquired by an unaffected direct path.

The MP4/MOV worker also implements `mp4-h264-aac-av-v1` and `mov-h264-aac-av-v1`: one H264 video track and one AAC-LC track, 48 kHz mono or stereo, 1024 samples per packet, an explicit two-byte AAC-LC configuration, zero-based timelines and identity edits. The authored AAC `roll` sample group must use zero preroll for the first packet and one preceding packet thereafter; that pattern is checked in source and output. QuickTime version-one AAC descriptions are admitted only with the supported packet fields. Other sample groups remain unsupported. Encoder priming already authored into the zero-based source is retained. Nonidentity priming/padding edits, surround layouts, SBR/extension configurations and other rates retain existing paths.

A/V qualification commands use the same MP4 candidate with `DEMUXE_TEST_AV=1` and `DEMUXE_AUDIO_CHANNELS=1` or `2` when running `test/browser-mp4.mjs`. The fixtures author 75 complete AAC packets over 1.6 seconds and retain encoder priming; they do not claim to reproduce the pre-encoding PCM without delay. Checks compare decoded PCM hashes and all 76,800 authored frames, both source track IDs, configuration/packet hashes, native decoded-audio progress after seeking, video progress and resource retirement.

The existing `ProviderRuntime` checks the exact provider/presenter identities and source envelope before acquiring anything. With both implementations available, FFmpeg retains its baseline preference; an explicit provider preference can select MediaBunny. Source availability and qualification precede preferences. A declared acquisition/integrity failure is terminal and does not become provider absence.

The existing native preparation owner also accepts inspected remote file representations up to 32 MiB. Admission requires the same complete format/track envelope plus pinned size and a strong ETag (or the existing explicit immutable contract). `RangeReader` retains HTTP range validation, allowed origins, authorization refresh, identity checks and transport deadlines on the main thread. The verified worker receives size/track facts and asks for bounded byte ranges; URLs, headers and authorization callbacks are not sent to it. Reads are serialized across A/V producers, capped at 4096 requests/32 MiB, with at most eight worker requests pending and a 30-second remote operation deadline. Admission policy snapshots are checked before reads and before output publication.

This complete-file remote path produces one bounded prepared Blob. The separately qualified incremental binding below delivers segments through the existing MSE owner. `DEMUXE_TEST_REMOTE=1 DEMUXE_TEST_AV=1` runs remote MP4/MOV A/V cases in `test/browser-mp4.mjs`; `test/browser-preview.mjs` also tests remote WebM and Matroska. The harnesses intercept HTTP locally and require no media server.

Preparation executes the verified self-contained module in a dedicated worker. The native owner retains load generations, prepared object URLs, startup verification, seeks and fallback policy. Cancellation terminates the worker; there is no global coder registration. Deployment CSP must allow the verified Blob module worker (`worker-src blob:`). The implementation does not use MediaBunny's automatic conversion pipeline.

Build candidate assets from the repository development environment:

```sh
node packages/provider-mediabunny/build.mjs /tmp/demuxe-mediabunny-candidate
node packages/provider-mediabunny/test/package-build.mjs /tmp/demuxe-mediabunny-candidate
node packages/provider-mediabunny/build.mjs /tmp/demuxe-mediabunny-mp4-candidate mp4
node packages/provider-mediabunny/test/package-build.mjs /tmp/demuxe-mediabunny-mp4-candidate
```

The output manifest is a **candidate**, not qualification. Compose it with the maintained FFmpeg/mpv providers. MediaBunny admission requires both the application's reviewed individual identities and one reviewed `qualifiedCompositions` record for the exact recipe, binding, preparation provider and presenter. The presenter must use a SHA-256 identity; the generic `demuxe-browser-v1` identity cannot authorize MediaBunny. The builder never adds qualification or changes the default registry.

For a composed package, `scripts/deploy-providers.py --content-addressed-presenter` opts into an identity derived from all files in the installed core inventory. The application must review and explicitly qualify the resulting identity and each permitted binding, including existing providers it intends to use with that presenter. For example, after obtaining reviewed identities from an independent qualification process:

```js
import {DemuxeRuntime} from 'demuxe';

const runtime = new DemuxeRuntime({
  assetBase,
  qualifiedProviders: {
    ...reviewedExistingProviders,
    'mediabunny-mp4-file-preparation': reviewedPreparationIdentity,
    'browser-prepared': reviewedPresenterIdentity,
  },
  qualifiedCompositions: [{
    recipeId: 'native-remux',
    bindingId: 'mediabunny-mp4',
    sourceProfiles: ['local:pthread:mp4-mov-avc-aac-2ch'],
    implementationIdentities: {
      'mediabunny-mp4-file-preparation': reviewedPreparationIdentity,
      'browser-prepared': reviewedPresenterIdentity,
    },
  }],
});
```

The source profile is part of the same reviewed record as the identities. Supported names use `local:` or `remote:`, then the remux runtime (`pthread:`, `jspi:`, or `asyncify:`), followed by `webm-matroska-vp8-video`, `mp4-mov-avc-video`, `mp4-mov-avc-aac-1ch`, `mp4-mov-avc-aac-2ch`, `mp4-mov-aac-1ch`, or `mp4-mov-aac-2ch`. AAC profiles require the existing 48 kHz source guard. The names group the containers Demuxe’s probe reports together; a grant must cover the entire corresponding guarded envelope. Streaming requires a video profile. Further worker checks still reject unsupported timing and configuration.

This registry is application-owned: neither a deployment manifest nor a content hash establishes that media, browsers or backup behavior were qualified. Admission still applies the source-profile guard, and the worker may decline unsupported inputs.

The build retains upstream MPL notices and emits `Apache-2.0.txt`, `MPL-2.0.txt`, `NOTICE.txt`, and `mediabunny-1.63.0-source.tar.gz` alongside the worker. Source inventory hashes include the exact JavaScript buffers supplied to esbuild plus preferred upstream TypeScript source. The MP4 build uses distinct `NOTICE-mp4.txt` and `mediabunny-mp4-1.63.0-source.tar.gz` names, allowing both profiles to be deployed together. The source archive is a separate legal/source download; it is deliberately absent from the runtime acquisition closure.

For the browser qualification harness, first build a candidate and set `DEMUXE_RUNTIME_CANDIDATE` to its output directory. The default source/assets roots assume this package lives in a complete Demuxe checkout. `DEMUXE_CORE_SOURCE_ROOT` and `DEMUXE_CORE_ASSET_ROOT` can select explicit source and asset trees for isolated validation. `DEMUXE_BROWSER_EVIDENCE` writes a receipt only after every assertion passes, binding the exact worker and test presenter identities to its fixture/browser envelope.

Default npm-loader inspection/preview factories do not constitute per-format transfer qualification. Applications requiring format-specific delivery should provide an appropriately bundled `load` implementation and verify its emitted graph. Both separately built preparation entries have their emitted graphs checked by the package validator; each excludes the other container parser. `test/browser-mp4.mjs` uses the MP4 candidate through `DEMUXE_RUNTIME_CANDIDATE` and can write an automatic receipt with `DEMUXE_BROWSER_EVIDENCE`. It verifies MP4 and MOV startup, seek/fresh-frame progress, decoded color, configuration/packet hashes, unqualified non-acquisition, direct-path non-acquisition and worker/object-URL retirement.

Broader MP4/MOV/Matroska profiles, browser-matrix qualification and production release approval remain unfinished phases of the adapter design. Existing codec slices remain in place. They must not be inferred from the finite VP8/AVC fixtures. The package stays private and its publication guard stays enabled.

## Incremental streaming prototype

The private `mp4-stream` candidate emits initialization/media segments through the existing `RemuxPlayer` presentation owner. It adds no playback clock or MSE loop. A one-record handoff blocks producer writes while the owner consumes a fragment. Source preflight verifies authored sample tables and packet metadata before initialization, limits GOP bytes and rejects timelines the output clock cannot represent exactly. Packet submission merges A/V by timestamp to avoid an unbounded per-track lead. Seek reopens at a video keyframe with one preceding AAC packet, retaining the owner's one-second timeline bias. Local inputs remain limited to 32 MiB and the finite classic AVC/AAC envelope. This is not a general large-file profile.

`stream-preparation.js` owns the local input; `worker-stream.js` installs one generation per worker. `RemuxPlayer` accepts an explicit internal `producerFactory` and retains SourceBuffers, scheduling, startup deadlines, seek/reopen and cleanup. Destroying during factory acquisition aborts it and retires a late worker. The source archive and npm files include these helpers. The separate worker has its own candidate provider ID and executable identity, not the complete-file worker's qualification.

```sh
node packages/provider-mediabunny/build.mjs /tmp/demuxe-mediabunny-stream-candidate mp4-stream
node packages/provider-mediabunny/test/package-build.mjs /tmp/demuxe-mediabunny-stream-candidate
DEMUXE_STREAM_RUNTIME_CANDIDATE=/tmp/demuxe-mediabunny-stream-candidate \
  DEMUXE_TEST_AV=1 DEMUXE_AUDIO_CHANNELS=2 \
  node packages/provider-mediabunny/test/browser-stream.mjs
```

The Chrome integration test verifies independently checked worker bytes, real MSE append/playback, seek/fresh video and audio, cancellation during acquisition, and worker/input/URL retirement. Its separate finite in-process drain of the same producer checks compressed packet hashes and decoded PCM hashes/extent. Collector byte statistics exclude input/cache, muxer, browser media and process memory; they are not retained-memory or performance qualification.

`ProviderRuntime.canStreamFile` admits this separate binding only after complete source facts and exact worker/presenter qualification. `streamFile` acquires verified bytes once, owns a worker/Blob URL lease per generation and retires it on cancellation or runtime destruction. `NativePlayer` installs that producer through the existing remux owner and verifies startup. Explicit profile rejection can return to the maintained preparation path; acquisition/integrity failures remain terminal. Qualified FFmpeg and complete-file providers retain baseline priority unless an explicit `media.prepare.file` preference selects streaming. Unaffected direct sources acquire no streaming bytes. Set `DEMUXE_STREAM_NATIVE=1` in the command above to test the actual Runtime/NativePlayer composition instead of direct factory injection. Neither harness exercises full public-player release deployment. Broader authored fixtures, browser coverage, measured resources and release gates remain open. Neither streaming qualification nor automatic activation is inferred from the candidate manifest.

The streaming binding also accepts inspected remote MP4/MOV files up to 32 MiB with a pinned size and strong ETag or the existing immutable contract. `ProviderRuntime.streamRemote` opens the existing main-thread `RangeReader`; the optional worker receives only size/track facts and bounded read replies. Source URLs, headers, allowed origins and refresh callbacks stay in Demuxe. The stream worker uses the same explicit `CustomSource` path as the core lease; it never uses SDK URL transport.

The read bridge admits at most eight pending requests and 4096 requests/64 MiB of logical read bytes per generation, allowing bounded metadata/preflight and packet passes over the finite input. It hides RPC messages from the presentation owner, transfers exact owned buffers and preserves original main-thread source errors. Reads have a 30-second deadline, including queue time; idle playback has no read timer or whole-operation timeout. The existing transport also retains its own deadlines/retry policy. Source-policy snapshots are checked at every RPC/output boundary and between HTTP blocks. Every seek reopens against the same inspected identity; an ETag change is `SOURCE_CHANGED`. Generation retirement closes transport before killing the worker and revoking its URL.

Use `DEMUXE_STREAM_NATIVE=1 DEMUXE_TEST_REMOTE=1 DEMUXE_TEST_AV=1` (add `DEMUXE_STREAM_MOV=1` for MOV) with `test/browser-stream.mjs` for the actual remote native composition. The generated stereo/mono fixtures span several HTTP blocks, retain authored AAC priming, and test startup, seek/fresh output, authorization refresh, denied access, identity change on reopen, cancellation during worker reads, policy mutation and complete retirement. The finite in-process packet/PCM drain remains separate evidence from remote worker playback. The public fixture compositions below pass; broader public release qualification and general large-file/container coverage remain open.

## Format-specific inspection and preview delivery

```js
import {createMediaBunnyInspector} from '@demuxe/provider-mediabunny/inspect/mp4';
import {createMediaBunnyPreviewProvider} from '@demuxe/provider-mediabunny/preview/mp4';
const inspector = createMediaBunnyInspector();
const preview = createMediaBunnyPreviewProvider({getSource: id => currentSources.get(id)});
```

The MP4 entries pin MP4/MOV; the WebM entries pin WebM/Matroska. Source imports can share one SDK instance through the application's bundler. `node build-delivery.mjs /absolute/output` also creates four self-contained browser bundle candidates and records emitted graph, exact compiled-input hashes, byte counts and SHA-256. The build rejects unrelated demuxers, conversion code, Wasm payloads and external imports. These checks describe transfer closure, not browser playback qualification. Standalone bundles contain independent SDK instances; avoid mixing their SDK class objects or custom codec registrations. The qualification harness separately loads a full SDK for fixture/configuration controls and can report the upstream duplicate-load warning; that full fixture SDK is not part of these bundle-size claims.
