# Demuxe CPU opportunity inventory — 2026-09-23

This is a route and cost investigation, not a proposed change to automatic playback. The checkout had substantial pre-existing edits, including engine and routing files. The new comparison uses the frozen `build/head-to-head/assets-passing-cpu-exploratory-20260923-01` snapshot; it does not silently relabel that snapshot as the edited working tree. CPU means summed CDP Chrome-process CPU divided by steady wall time. It excludes external media services, the fixture server, GPU energy, and display quality.

## Evidence rules

- **Matched:** same fixture and runtime, alternating arms in one campaign, accepted playback and CPU windows. Only these numbers support a route comparison.
- **Exploratory:** a different campaign, a bounded pass without full fidelity, or unstable ranges. Useful for finding cost centers, not ranking measured speed.
- **Correctness only:** route, pixels, audio, seeks, EOF, or teardown without an accepted CPU window.
- **Insufficient:** missing fixture, failed playback, or absent component counters.

The README table combines older matched cross-player medians, a separate 45-case forced Software campaign, and a supplemental pass-cell CPU campaign. The latter did not repeat fidelity checks. The bold values on rows populated from different campaigns must not be compared as though paired. In particular, MPEG-2 Demuxe Auto 55.5%, forced Software 48.0%, Movi 35.0%, and AVPlayer 37.7% do **not** form a four-arm matched result. The first two numbers are from separate supplemental/Software campaigns; the last two are from the older cross-player campaign. Similarly, H.264/AC-3 61.2%, 68.9%, and AVPlayer 52.1% are exploratory readings, not a matched speed ordering.

The later [routing-isolation supplement](../../results/head-to-head/routing-isolations-20260923-01/REPORT.md), now on main, supplies its own matched MPEG-2/AC-3 and H.264 AC-3/E-AC-3/DTS controls. It supersedes those particular older README leads within its fixture and build; it does not make numbers across campaigns interchangeable. Its 5.1 controls use a marked stereo-output screen and explicitly leave discrete-channel fidelity unqualified.

The table deliberately keeps current route, fidelity and campaign provenance together. It does not imply that `native-direct` preserves original 5.1 channels or that an Atmos-tagged fixture verifies object rendering.

Current Hybrid owns one mpv/FFmpeg demux and audio decode. The browser WebCodecs decoder owns compressed video decoding; mpv still owns video scheduling, retained-frame presentation and A/V synchronization. `native/player.c` configures mpv float audio at the AudioContext rate, `ad-lavc-threads=1`, and `vd-lavc-threads=2`. `native/ao_browser.c` writes interleaved float PCM into an 8,192-frame Wasm ring. The active `web/filter-retained-engine-worker.js` (Hybrid) and `web/software-full-engine-worker.js` (Software) pump that ring into a separate shared PCM ring using the configured 2/6/8 channel count; `web/audio-worklet.js` reads and deinterleaves up to 128 frames each callback. The worklet reports consumed frames, and mpv's AO state uses that feedback plus output latency for synchronization. No evidence yet separates codec decode, mpv scheduling, resampling, layout conversion, PCM copying, worklet output or polling CPU.

The retained WebCodecs bridge allocates an FFmpeg software decoder context for recovery but opens it lazily only after browser decode failure; routine Hybrid playback does not appear to software-decode the same video a second time. mpv still processes compressed video packets and selected-frame state. A profile must distinguish that scheduler cost from duplicate decode instead of assuming both.

The source shows no *second container demux* inside Hybrid's main engine. Duplicate demux is present when a Native remux or Direct path also opens the separate mpv subtitle service. The smallest audio separation PoC is to keep the existing mpv audio/Worklet bridge, set `vid=no`, present video through a browser-only native/remux source, and drive bounded seek/pause/rate synchronization from the browser clock. That isolates the cost of mpv's Hybrid video scheduler without rewriting the decoder. It would introduce a second demux unless it reuses native preparation's packets, and it would no longer inherit mpv's single-clock A/V behavior. Only if that PoC shows a material, correct gain should an even smaller FFmpeg audio demux/decode service replace mpv. Such a service must supply source-time and output-time mapping, seek epochs, pause/rate handling, underflow recovery, track changes, EOF and latency correction. The earlier [pipeline separation study](../../results/pipeline-separation/README.md) built packet-only remux and YUV presenter proofs, but explicitly deferred audio-only conversion; encoding to AAC would alter quality and priming, so the current question is original-track software decode/output with browser video, not a silent transcode.

| --- | --- | --- |
| Container and track selection | mpv/FFmpeg reads the source and selects streams in Hybrid | Count demuxed video/audio packets, read bytes and scan time; determine whether a proposed audio-only reader can skip video payload parsing without a second full source read. |
| Video packet transfer | mpv forwards selected compressed video to the retained WebCodecs worker | Count packet bytes, JS allocations and transfer copies; existing retained mode already avoids the former software replay cache. |

| Format, resample, channel handling | mpv requests float output at AudioContext rate and configured 2/6/8 channels | Record input format/rate/layout, filter graph choice, output format and time in each filter. Avoiding resample is possible only when rates match exactly; channel policy must retain discrete channel identity where qualified. |
| Wasm ring write and worker transfer | Interleaved float AO ring, then JS copies into a second shared ring every active worker tick | Count frames/bytes and time each copy with channel count and ring wrap. Isolated copy PoC gives a tiny upper bound at 48 kHz, so do not make this the first architecture change. |
| Worklet and WebAudio | One 128-frame callback deinterleaves to planar output; WebAudio supplies output latency | Measure callback CPU, underruns, actual layout and device rate. A direct shared ring still needs a safe, fixed memory lifetime and seek-epoch protocol. |

The [copy-stage probe](audio-ring-copy.mjs) verifies that a channel-aware block copy is byte-equivalent to the active per-sample loop for 2, 6 and 8 channels, including ring wrap. On this Node arm64 host the current-loop model took 0.22/0.41/0.49 ms per 48,000 frames versus 0.023/0.045/0.050 ms for block copies. These roughly 9–10× **stage** ratios apply to a sub-millisecond-per-second stage, not a meaningful whole-player gain. This probe does not include Wasm memory growth, Atomics, worklet callbacks or browser scheduling. An older unused `web/engine-worker.js` hardcodes two channels; the active Hybrid and Software workers do not. PCM transport cost cannot explain tens of CPU points without component timing.

AVPlayer's pinned package contains separate FFmpeg codec Wasm assets and an `AudioDecodePipeline`/`AudioRenderPipeline`; its bundled pipeline has resampler and stretch components. Movi's pinned source uses FFmpeg software audio decoding and `AudioBufferSourceNode` scheduling, with small-frame coalescing for TrueHD/DTS. These implementation observations show that neither competitor needs mpv for audio, but do not prove fewer copies or better synchronization. Movi's AC-3/DTS comparison cells often fail or have lifecycle limits. The matched HEVC/AC-3 row favors Demuxe over AVPlayer, so AVPlayer is an oracle for *possible component separation*, not a universally faster audio path.

The highest-value audio profile should record, per accepted 20-second window: selected route/decoder, mpv demux-read CPU, audio decode CPU, filter/resample CPU, AO write CPU and frames, worker copy CPU and bytes, worklet callback CPU and underruns, video scheduler CPU, source read counts, sync error and output channel map. Counter reads should be sparse and excluded from a matched production CPU window or included identically in all arms. Compare audio-muted and video-disabled ablations only as attribution controls; they are not correctness substitutes.

## Subtitle service by stage

| Family | Demux / parse | Timing | Render / composition | Narrowest promising service |
| --- | --- | --- | --- | --- |
| SRT | Text cue extraction; currently mpv reads container again | Start/end events and seek epoch | DOM/text canvas only on cue or geometry change | Selected subtitle packet extraction + simple cue scheduler; mpv fallback |
| mov_text | ISO BMFF sample text and tx3g style parsing | Sample duration and edit-list timing | Text/style renderer on cue or geometry change | Small parser after exact style and edit-list tests; mpv fallback |
| ASS/SSA | Dialogue, headers and attachments | Event clock, animations and karaoke | libass bitmap/tile changes and upload | Existing independent libass path plus demuxed packets; retain mpv for unsupported scripts/fonts |
| PGS/VobSub | Compressed bitmap packets, palettes, object state | Composition windows, clear events and seek reset | Changed rects only | FFmpeg subtitle decoder + bounded bitmap compositor; mpv fallback |

The existing service explicitly sets `vid=no` and `aid=no`, and current tests observed zero mpv A/V chains. It still initializes mpv, FFmpeg demux, a 64 MiB Wasm heap, pthreads and an I/O worker. The browser controller runs `requestAnimationFrame` while playing and sends a render RPC whenever the timestamp string changes. The service returns `unchanged` on stable overlay IDs, avoiding many bitmap transfers, but it still polls/render-checks at display cadence. The retained matched SRT trials recorded 766–788 controller render completions against only 7 bitmap updates over each full lifecycle; ASS had 781–789 renders and 7 bitmap updates. These are cumulative startup, playback, seek and EOF counters, not steady rates or isolated CPU attribution. They demonstrate redundant request checks even when upload reuse works. Event-driven text cues and a bounded next-change deadline could remove that polling; ASS animations, bitmap clear events and seek/resize invalidation require a format-aware fallback cadence. The service currently scans a bounded set of startup timestamps to prove a cue exists; this may reject late valid cues and can cause repeated seek/decode work. Its font files are loaded once per service instance; repeated font scanning across source replacement is plausible but unmeasured.

The service already copies only the changed subtitle rectangle from mpv into Wasm and converts that rectangle to an `OffscreenCanvas`. On a change, `web/mpv-subtitle-worker.js` then draws it into a **full-video-size** canvas and transfers that full canvas as an `ImageBitmap`; the controller draws it again on its overlay canvas. The `bytes` diagnostic counts mpv's changed rectangle, not this whole ImageBitmap. A cropped bitmap plus offset would remove the full-size intermediate, but must retain alpha/composition order and geometry on resize. Measure allocated bitmap dimensions and transfer CPU on ASS/PGS/VobSub before changing the ABI.

The [text-cue scheduling PoC](text-cue-poc.mjs) used host FFmpeg to extract the selected text stream from the exact SRT and mov_text fixtures. Both yielded one cue from 0.5 to 35.8 seconds. A pure cue-state scheduler matched the six authored present/absent/seek sample times; at a modeled 30 Hz, 1,080 checks corresponded to only two cue transitions. This proves the event-cadence hypothesis on these fixtures only. It does not implement Demuxe's container extraction, tx3g styling, edit-list timing, browser overlay, or ASS/bitmap semantics, and it provides no process CPU result.

## Software video and competitor inference

The older MPEG-2 result suggested Movi might be materially cheaper: its 35.0% and AVPlayer's 37.7% share an earlier campaign, while Demuxe's 55.5% came from a newer CPU-only run. The fresh [matched four-arm campaign](../../results/performance-opportunities/mpeg2-performance-20260923-d/REPORT.md) did **not** confirm that large gap. It used one frozen asset snapshot, 3 rotating-order rounds per lane, headed Chrome, 5-second warmup and ~21-second steady windows. All 12 performance trials passed and the result integrity verifier passed. Correctness passed startup, marked moving picture, audio, pause/rate, seeks, EOF and cleanup for all four lanes. All measured windows submitted approximately 629–637 frames against 627–635 expected; those are route-specific submission counters, not identical physical display proof.

| --- | ---: | ---: | ---: | ---: |
| Demuxe Auto, `software` | 58.3% | 67.6% | 72.4% | 67.6% |
| Demuxe forced Software, `software` | 58.8% | 61.6% | 72.0% | 61.6% |
| Movi default | 64.1% | 53.4% | 60.2% | 60.2% |

The ranges overlap substantially. Movi was lower than Auto in two of three rounds and higher in one; the median difference alone is not a reliable win. Auto and forced Software used the exact same `software` route in every trial. Their CPU difference is run variability or non-route setup/scheduling variation, not evidence that Auto duplicates decode. The earlier large Movi gap was therefore a campaign-mixing lead, not a confirmed bottleneck.

Demuxe's exposed Software timers show 1.66–2.40 seconds inside `_web_render` and 0.45–0.64 seconds in frame copy/`putImageData` over each ~21-second window, with about 630 presented frames and 3,073–3,139 worker pump ticks. These are elapsed stage timers, not isolated CPU seconds, and `_web_render` includes mpv scheduling/presentation work rather than only libavcodec. The 320×180 fixture makes fixed per-frame/pump overhead a plausible target. A decoder-only, same-build profile and a higher-resolution exact-frame fixture are needed before claiming the MPEG-2 entropy decoder is slow.

The CDP process split sharpens that lead without proving a total win: Demuxe Auto's renderer processes consumed 4.2–4.9 CPU seconds per window versus Movi's 1.6–2.6; Demuxe GPU processes consumed 1.1–1.3 seconds versus Movi's 1.4–2.1. AVPlayer renderer consumed 3.0–3.5 seconds. Browser-main CPU was large and variable for every lane (about 6.8–9.1 seconds), which explains why summed whole-process medians do not cleanly rank the players. CDP process roles are not a decoder profiler, but the consistent renderer/GPU distribution aligns with Demuxe's CPU RGB/Canvas2D path and Movi's WebGL presenter. It makes presentation and per-frame scheduling a more specific next profile target than replacing MPEG-2 entropy decode.

Movi's pinned source uses FFmpeg software decode when WebCodecs has no codec string, calls `getFrameRGBA` (sws_scale), constructs a `VideoFrame`, and presents through a WebGL canvas. Its software decoder can skip non-reference frames at a deliberately reduced target FPS, and caps width to 1920 for software conversion. The current 320×180 campaign passes frame-submission gates and authored markers, so the source-level shortcuts are not proof of what Movi did in this particular run. Different high-resolution behavior must be tested separately.

The source-level work Movi clearly avoids is Demuxe's mpv render/scheduler bridge and Canvas2D `ImageData`/`putImageData` presentation; it still performs FFmpeg decode and RGBA conversion on this software path. AVPlayer clearly avoids mpv through its demux/decode/render pipelines and codec-specific Wasm assets, but its bundled implementation and process counters do not isolate whether it saves copies, decode time or scheduler CPU. Neither competitor provides evidence that a new MPEG-2 decoder is needed: the fresh whole-process result is tied within large variation, and any renderer shift is partly offset by GPU/browser process work.

Demuxe's Software path uses FFmpeg decode, mpv scheduling, then a CPU RGBA copy and `putImageData` in the default presenter. The experimental YUV backend bypasses RGB conversion for 8-bit YUV420P SDR but still stages Y/U/V uploads. The earlier H.264 SIMD work reduced decoder-only CPU by 23–34% and whole-browser Software CPU by 15.81% on its matched movie; it is already integrated for those H.264 kernels and cannot be counted again as a new opportunity. Retained Hybrid frames also already avoid its former copy-back path. The [WebGPU luma/IDCT prototype](../webgpu-compute-decoder/REPORT.md) proved worker/GPU-resident presentation for a repeated ProRes-derived block, but did not bridge real ProRes coefficients or show a whole-player CPU win. On ProRes 10-bit 4:2:2 the existing YUV presenter fell back to RGB. Prior Vulkan/compressed-domain and tile research also establishes narrow components or blocked browser execution, not a working general video decoder. For MPEG-2/MPEG-4/ProRes/FFV1/DNx/CineForm/HuffYUV/UTVideo/MagicYUV/VC-1, profile the current FFmpeg decoder and presenter first; only pursue compute decoding if entropy/reconstruction dominates *and* an exact browser GPU proof runs on the target media.

## Decision gates

The fresh [correctness run](../../results/performance-opportunities/correctness-20260923-b/REPORT.md) passed MPEG-2/AC-3 Auto, forced Software, Movi and AVPlayer on the same asset snapshot. Auto and forced Software both reported the exact `software` route at EOF. Thus the older 55.5% vs 48.0% readings are not evidence of a Hybrid route penalty; they are measurements of the same route in separate campaigns. The H.264/AC-3 lanes were **blocked** from comparison by the catalogue's explicit stereo-output limitation; a screen pass would not establish discrete 5.1 fidelity. The separate [three-lane MPEG-2 pilot](../../results/performance-opportunities/mpeg2-correctness-20260923-a/REPORT.md) also passed. Neither correctness run contains CPU evidence.

The fresh [HEVC audio correctness run](../../results/performance-opportunities/audio-correctness-20260923-a/REPORT.md) passed six lanes: HEVC Main10 + AC-3 and + E-AC-3, each under Demuxe Auto, forced Software and AVPlayer. Auto selected `hybrid`, forced Software selected `software`, and AVPlayer used its custom route. This is a valid route contrast for the next matched CPU run; it is still a bounded stereo-output, synthetic-media screen rather than discrete surround, HDR color or spatial-audio qualification.

A separate [HEVC + DTS correctness run](../../results/performance-opportunities/dts-correctness-20260923-a/REPORT.md) passed the same three route types under the frozen comparison harness. Its CPU run is separate from AC-3/E-AC-3 and must be interpreted within its own fixture/campaign.
