# Unified Hybrid and Software experiment
Hypothesis: one full engine with mode-dependent presentation can replace separate full Hybrid and Software binaries without codec modularization or FFmpeg changes.
Baseline: frozen granular-engine-loading screen runtime plus matched full-study baseline binaries. Candidate: same runtime, one full Hybrid-derived binary, Software rotation capability selected per instance, retained-only subtitle callbacks, shared per-player fetch/compile cache.
Scope: isolated lab integration; existing shipping routes and unrelated work preserved. Separate instances keep independent heaps and workers. No claim of memory deduplication or seamless decoder handoff.
Correctness: Chrome Hybrid and Software H264/HEVC, Firefox Software H264/HEVC; seek backwards/forwards, subtitles, independent RGB oracle plus inverted negative control, audio tone/progress, source replacement, Hybrid failure to Software, worker/process teardown. Additional rotation fixture checks because VO capabilities differ. Explicit Software must not activate browser decoder. Asset requests and compile identities must prove same binary reuse.
Performance only after relevant picture gates: three alternating baseline/candidate pairs per browser for prepare-all at aggregate gzip 10 Mbps, 80 ms response delay; user HEVC fixture. Record prepare time, selection-to-progress, sum, bytes, compile count, fallback. Three Chrome no-preparation recovery pairs at same network. Local first-use pair per route as regression screen. Target >=40% combined engine gzip savings, >=25% prepare-all median reduction; single-engine size no more than 5% above larger baseline. Report small sample limits, no physical latency/energy or memory saving claims.
Stop on wrong output or loss of fallback; preserve failed trials. Harder codec modules and shared runtime memory remain deferred.
