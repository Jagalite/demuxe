# Implementation boundaries investigated

The study distinguishes four mechanisms:

1. **Prepare selected existing engines.** Fetch and compile once; instantiate only when used. This shifts waiting ahead of selection and avoids duplicate compile work on that page. It does not eliminate the cost. Preparing every engine can compete with the useful engine for bandwidth; the paced-policy tests use one shared response bandwidth budget.
2. **Lean Hybrid static bundle.** Register the browser decoder independently, omit software video implementations from the FFmpeg registry, retain audio/subtitles and whole-engine fallback. Small routing/build change compared with dynamic linking; highest-confidence whole-player opportunity if its primary tests pass. Exact supported codec and color profiles still need qualification.
3. **Finite Software bundles.** Select common-video or HEVC-only runtime after metadata inspection; keep broad audio/subtitle support and a full-engine escape route. Lower first-download bytes, but repeated shared core code across bundles. A user who later switches to another codec can download more in total than with one full runtime. Registry order is part of behavior: preserve the upstream list order. Runtime failures within a recognized codec still need full fallback, not only a filename/codec-name gate.
4. **Runtime decoder side modules.** A real H264 FFmpeg decoder/parser is built as PIC and loaded into a pthread host on demand. Explicit required-symbol retention is essential: default MAIN_MODULE=1 bloats the host, while declaring a side module as a link dependency loads it eagerly. MAIN_MODULE=2 plus a generated external-symbol manifest enables true deferred loading. This proves a component mechanism, not mpv integration.

A production side-module design would need a stable, versioned ABI over packet submission, frame buffers, errors, flush, reset and destruction. Options are a common FFmpeg core with dynamically supplied decoder descriptors (requires replacing the current static registry), or a per-module facade that owns private codec state (simpler boundary, potentially duplicates utility code). The component probe uses the latter and returns checksums rather than presenting frames; it cannot establish player copy/latency costs.

All modules must share a compatible Wasm memory/table/thread model; do not mix arbitrary Emscripten or FFmpeg versions. Module loading and symbol resolution synchronize pthread tables. Load errors must fail boundedly and leave a working whole-engine fallback. Cancelled loads, track/source replacement, seek/drain, data-layout compatibility, growth of code retained over a page lifetime, and worker teardown need integrated regression tests. A successful dlclose/reload test is not proof that code memory was reclaimed.

Metadata stripping and HTTP compression are packaging changes, separate from component selection. The existing initial screen measured gzip savings for metadata stripping; neither those savings nor prior component-study CPU percentages are added to this study's measured results. Brotli/CDN/cache behavior can change transfers; this study reports its actual gzip model rather than assuming all deployments match it.

Recommendation should be derived in order: qualified whole-player savings first; startup policy tradeoffs second; component-module proof and its remaining integration risks third. Research completion does not enable new production routing.

Cache identity is a necessary integration change. The lab server uses one URL to substitute binaries under no-store responses; a production bundle selector must use immutable profile/version URLs. The existing component preparation cache is keyed at engine/component granularity, so it must not return a compiled common/HEVC binary when the caller requires full Software. Include the binary identity in cache keys and validate dependency versions. A cached/prepared full engine can be preferable to downloading a smaller cold profile; never assume smaller bytes always imply a faster selection.

Before a file is chosen, the application cannot know its codec. Sensible options are preparing the inspector and known likely engines, honoring an explicit user profile preference, or preparing everything with the total cost visible. After inspection, load the smallest qualified compatible bundle. If full Software is already prepared, reuse it. If a later source/track needs another profile, account for duplicate core bytes and bounded handoff. The lab admission probe is intentionally separate and can duplicate the player's own probe; an integration should reuse one inspection result and include malformed/unknown input in the full-engine fallback policy.
