# Full feasibility study: granular loading

Authorized follow-up to screen-01. Isolated research prototypes only. Preserve all previous manifests and outputs; no shipping source/build/routing changes. User media stays outside repository. Reuse the frozen screen-01 runtime and fixtures by immutable path/hash so differences are attributable to binaries and explicit experimental loading policy.

Questions: (1) Can independent browser decoder admission make lean Hybrid correct? (2) How much does this save in real startup, transfer, compilation and resident-memory proxies? (3) Can a reduced common-codec Software profile help Firefox while preserving a full fallback? (4) Is true FFmpeg runtime module loading viable with this exact pthread/Wasm toolchain? (5) How do lazy, selective and all-component preparation compare, including preparation cost and fallback penalties?

Prepare: matched baseline, admission-only control and lean Hybrid; common-video Software build retaining H264/HEVC/VP8/VP9/AV1, audio/subtitles and full-engine fallback; actual FFmpeg side-module build/load/decode probe where the existing archives permit it. Build logs and failed prototypes retained. No toy-module speed is claimed as player speed.

Correctness: baseline vs candidate actual decoded H264/AAC/ASS, HEVC user file, additional VP8/VP9/AV1 and unsupported-codec fallback as applicable. Pixel oracle with declared matrix (MAE <=6), exact or tolerant baseline equivalence, wrong-picture negative control; 1kHz tone and progress; seek backward/forward, pause/resume, replacement, injected decoder failure, destroy/OS process exit. Preserve known baseline subtitle backing anomaly; do not assert full subtitle rendering correctness from matching it. Unsupported codecs must not silently produce wrong output. Per-codec unsupported browser routes count as fallback tests, not candidate decoding.

Performance only after each tested profile passes correctness. Five sequential alternating pairs for the primary user-file Chrome baseline/lean comparison local and gzip WASM paced at 10Mbps/80ms. Three pairs for Firefox user-file Software comparison if its candidate qualifies. Browser launches excluded, fresh profiles, page foreground checked; cache warmth and host background processes disclosed. Other policy tests are separate exploratory samples, not pooled with primary results. Record open/play/progress timestamps, asset sizes, selected engine, worker/process cleanup, phase fetch/compile timings where directly observable. RSS/CPU are proxies, not peak memory or energy. Physical AV/hardware acceleration not inferred.

Success for a production proposal: >=20% gzip component reduction, >=10% and >=100ms median primary startup benefit under one declared condition, no correctness/fallback regressions in tested profiles. Report paired differences, raw samples and bootstrap uncertainty; no selective removal of slow samples. Network model applies to WASM requests only. Warm/repeated and preprepared selection timings charge preparation separately. Full-module fetch/instantiate costs and fallback second-engine cost must be visible.

Scope depth: fully investigate these mechanisms through faithful build/runtime tests or a concrete source/toolchain blocker, then deliver a decision and integration requirements for each. A failed prototype can be diagnosed and revised in a new named variant, preserving failure. No arbitrary effort limit from screen-01 applies. This is a feasibility study, not exhaustive all-codec/device/endurance/release qualification.
